# Local vs Shared Ignore Rules

This concept distinguishes between ignore rules that stay private to one checkout and ignore rules that should be shared across all contributors.

## Core Distinction

- **Local ignore** means adding paths to `.git/info/exclude` so the repository state stays untracked only in the current clone.
- **Shared ignore** means adding patterns to `.gitignore` so every contributor follows the same ignore behavior.

The choice reflects [[concepts/consent-first-tooling]], [[concepts/local-vs-shared-configuration]], and [[concepts/generated-content-governance]]: generated or environment-specific files should not be shared unless the team has explicitly agreed to that behavior.

## Policy Pattern

The source document describes a default policy for harness-specific profile adapters and tooling context:

- prefer **local-only** tracking behavior for harness-local adapter state;
- write adapter files locally;
- add those paths to `.git/info/exclude`;
- avoid editing `.gitignore` by default;
- do not commit the generated adapter files.

This keeps harness-specific runtime material aligned with [[concepts/runtime-adapter-management]] and [[concepts/permission-scoped-agents]] by reducing unintended repository-wide effects. The same boundary also supports [[concepts/tooling-context-isolation]] and [[concepts/local-tooling-boundaries]]: tooling context is user-scoped, not project truth.

## When Shared Ignore Applies

Shared ignore rules are appropriate when the ignored files are expected to be generated by every contributor or are part of a common workflow.

The document highlights `okf/wiki/tooling/` as a special case:

- all contributors generate harness build records there;
- shared ignore is therefore the correct default;
- use `.gitignore` for `okf/wiki/tooling/*`;
- keep `!okf/wiki/tooling/index.md` as an explicit committed exception;
- do not use `.git/info/exclude` for that directory.

This is an example of [[concepts/tooling-context-pages]] and [[concepts/tooling-navigation-exceptions]] where a shared repository convention overrides the normal local-only default. It also depends on [[concepts/tooling-context-governance]], since tooling pages are user-scoped but the committed stub and root navigation entry must remain coherent across clones.

## Decision Rule

A practical way to choose is:

- use `.git/info/exclude` for personal or harness-local adapter state;
- use `.gitignore` for repository-wide generated artifacts;
- commit files only when the team explicitly wants them versioned.

That keeps ignore policy aligned with [[concepts/human-in-the-loop-review]] and [[concepts/safe-automation]] instead of letting tools silently broaden scope. It also matches [[concepts/consent-first-workflows]]: the broader the sharing scope, the more explicit the agreement should be.

## Related Alias Handling

The same local-first logic applies to instruction-file aliases:

- prefer a local symlink to `AGENTS.md` when a harness needs a different filename;
- exclude the alias locally;
- only adopt it after confirming the requirement from documentation or user instruction.

This connects the concept to [[concepts/instruction-file-aliasing]] and [[concepts/harness-native-profiles]]. It is also consistent with [[concepts/minimal-tool-scoping]]: keep the scope of environment-specific adjustments as narrow as possible.
