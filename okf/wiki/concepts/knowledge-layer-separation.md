# Knowledge Layer Separation

Knowledge layer separation is the practice of keeping repository orientation, durable context, repeatable actions, and runtime-specific adapters in distinct surfaces so each can be loaded, maintained, and governed independently.

In agent-smith, this is the architectural rule that turns a repository into an [[concepts/agent-ready-repositories|agent-ready repository]] and keeps the knowledge compilation model usable across different harnesses. The README frames the repository as a progressive-disclosure system: raw sources are compiled into an interlinked wiki, while instructions and procedures stay in separate places so agents only load what they need when they need it [[concepts/progressive-disclosure]] [[concepts/context-action-separation]]. That same logic appears in the subagent profile adapter skill, which treats harness files as runtime projections rather than a source of truth.

## What each layer does

- `AGENTS.md` is the orientation layer: setup, toolchain basics, repository rules, and routing guidance.
- `okf/wiki/` is the context layer: durable knowledge, architecture notes, evidence, and provenance.
- `.agents/skills/` is the action layer: reusable procedures, validations, and workflows.
- Harness adapters are runtime projections only; they are not treated as source of truth.

The README also sharpens the boundary between these surfaces by describing the repository as carrying three portable skills: `agent-ready-context`, `skill-creator`, and `subagent-profile-adapter`. Those skills are the distributable product, while pinned `graphify` and `openkb` directories under `.agents/skills/` are vendored toolchain copies, not portable repository knowledge. That distinction reinforces that knowledge layers should be small, intentional, and role-specific rather than mixed together in one large surface.

## Why it matters

The repository guidance argues that agents repeatedly re-derive the same understanding unless knowledge is compiled into a reusable surface. Layer separation reduces that churn by giving each kind of information a stable home. It also supports [[concepts/durable-context]] by preserving knowledge across sessions, while keeping operational files concise and action-oriented [[concepts/action-oriented-documentation]].

The README adds that this separation is not just stylistic; it is what makes the repo effectively compilable. Orientation, context, and actions each have a different load pattern, and the system is designed so that contributors and agents can reason about them independently. That makes the repository easier to bootstrap, easier to maintain, and less likely to lose important conclusions between sessions.

The model also supports:

- [[concepts/documentation-architecture]] by assigning clear roles to distinct files and directories.
- [[concepts/knowledge-boundaries]] by preventing context from leaking into action files.
- [[concepts/skill-action-boundary]] by keeping reusable procedures in skills instead of in wiki pages.
- [[concepts/tooling-context-isolation]] by ensuring harness-specific details stay out of the project knowledge base.
- [[concepts/runtime-adapter-management]] by treating subagent/profile files as harness-specific projections.
- [[concepts/generated-content-governance]] by keeping generated surfaces scoped to their intended function.

## Source examples from the README and adapter skill

The README and adapter skill together present four main surfaces:

- `AGENTS.md` for orientation and repo rules.
- `okf/wiki/` for compiled knowledge and provenance.
- `.agents/skills/` for repeatable actions.
- Harness adapters for native runtime files that mirror the active environment.

The README is explicit that the repository did not escape its own process: its `AGENTS.md` and `okf/` knowledge base were generated by agent-smith running on itself. That self-application is an example of knowledge layer separation in practice: the generated orientation and context surfaces exist for contributors and agents, while the skills remain the reusable operational layer.

The adapter skill adds a stronger boundary than the README alone. It says the active harness should be detected from runtime signals, not merely from installed binaries, and that ambiguous cases should be resolved by asking the user. It also routes harness-specific knowledge into `okf/wiki/tooling/`, declares it in `okf/wiki/AGENTS.md`, and keeps it indexed as an outsider rather than allowing project concept pages to depend on it. That design preserves [[concepts/tooling-link-policy]] and keeps runtime files small enough to remain readable and safe.

## Related governance ideas

Knowledge layer separation is closely tied to these concepts:

- [[concepts/generated-content-governance]] — generated surfaces should stay within their intended scope.
- [[concepts/knowledge-lifecycle-governance]] — source changes should trigger the right kind of regeneration.
- [[concepts/documentation-cohesion]] — the layers should fit together without duplicating responsibilities.
- [[concepts/reserved-wiki-files]] — wiki structure should remain predictable and machine-navigable.
- [[concepts/tooling-link-policy]] — tooling pages may point into project knowledge, but not the other way around.
- [[concepts/adaptive-harness-detection]] — runtime-specific boundaries depend on evidence-based harness identification.
- [[concepts/runtime-ambiguity-resolution]] — unclear harness state should be escalated rather than guessed.

## In practice

A repository that follows knowledge layer separation becomes easier for agents to bootstrap, maintain, and validate. Orientation stays lightweight, context stays durable, actions stay reusable, and runtime adapters remain harness-specific. The result is a repository that is easier to reason about incrementally and safer to operate over time.
