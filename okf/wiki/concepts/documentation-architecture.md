# Documentation Architecture

Documentation architecture is the way a repository's written guidance is arranged into files, sections, and relationships so people and tools can find, understand, maintain, validate, and regenerate it. In this wiki, the concept is grounded in the structural patterns surfaced by [[summaries/graphify-report]], the agent-facing template summarized in [[summaries/agents__skills__agent-ready-context__assets__agents-md-okf-ready-template-md]], the bootstrap guidance captured in [[summaries/agents__skills__agent-ready-context__references__agent-ready-bootstrap-md]], the offline-first spec-check workflow described in [[summaries/agents__skills__agent-ready-context__references__official-okf-spec-web-check-md]], the OKF quality baseline summarized in [[summaries/agents__skills__agent-ready-context__references__okf-quality-md]], the OpenKB lifecycle policy summarized in [[summaries/agents__skills__agent-ready-context__references__openkb-lifecycle-md]], the fallback skeleton generator summarized in [[summaries/agents__skills__agent-ready-context__scripts__build_okf_skeleton-py]], the AGENTS managed-section updater summarized in [[summaries/agents__skills__agent-ready-context__scripts__merge_agents_md_okf_section-py]], the repository build workflow summarized in [[summaries/agents__skills__agent-ready-context__references__workflow-md]], the agent-ready-context skill itself summarized in [[summaries/agents__skills__agent-ready-context__SKILL-md]], the subagent/profile adapter skill summarized in [[summaries/agents__skills__subagent-profile-adapter__SKILL-md]], the tooling link policy validator summarized in [[summaries/agents__skills__subagent-profile-adapter__scripts__validate_tooling_link_policy-py]], the repository inventory captured in [[summaries/repo-snapshot]], and the repository-level design explained in [[summaries/README-md]]. The agent-ready-context skill sharpens that model by making the repository agent surface split by responsibility: skills are actions, the OKF wiki is durable context, and `AGENTS.md` is orientation and routing. The README widens the same architecture into an explicit product and operational model: `AGENTS.md` is the orientation surface, `okf/wiki/` is the compiled knowledge surface, `.agents/skills/` is the actions surface, and harness adapters are runtime-only projections. That framing reinforces that documentation architecture is not just page layout; it is a division of labor across durable knowledge, operational procedure, runtime-specific outputs, and validation surfaces.

## What the concept means here
In this repository, documentation architecture is not just about having documentation. It is about assigning different kinds of guidance to the right layers, defining how those layers relate, and making the navigation order explicit for both humans and agents.

The Graphify report sharpens that pattern by showing a repo-scale map with 472 nodes, 550 edges, and 54 communities spread across 63 files and about 79,281 words. It does not just confirm that documentation exists; it shows which files act as hubs, which topics cluster together, and where cohesion breaks down. The report highlights major navigation centers such as `README.md`, `AGENTS.md`, `OpenKB Wiki Schema`, `What You Must Do When Invoked`, and several build and validation scripts. It also shows that many important abstractions are anchored in workflow and policy documents rather than in code alone. The README complements that view by making the same architecture legible as a repository product: orientation in `AGENTS.md`, durable context in `okf/wiki/`, actions in `.agents/skills/`, and runtime adapters as harness-specific projections. The AGENTS template adds a complementary architectural pattern: human-facing documentation belongs in `README.md` and `docs/`, agent-facing operational guidance belongs in `AGENTS.md`, durable evidence-backed knowledge belongs in `okf/wiki/`, and repeatable procedures belong in `.agents/skills/`. The bootstrap reference sharpens that pattern by treating `okf/wiki/` as the durable source of truth, `graphify-out/` as an exploration aid rather than final authority, and `AGENTS.md` as a routing layer that should stay concise. The managed-section merge script makes that architecture operational inside the repository by inserting or replacing only a bounded OpenKB guidance block in `AGENTS.md`, preserving unrelated project-specific instructions while standardizing the routing order and maintenance policy. The agent-ready-context skill also makes the pipeline explicit: it distinguishes deterministic source staging from wiki compilation, warns against writing generated files directly into `okf/raw/` or `okf/wiki/`, and treats the wiki as a compiled knowledge surface rather than a freeform notes area. The README extends that same boundary with an explicit product definition: the skills are the distributable actions layer, the wiki is the compiled knowledge layer, and vendored tool skills are not part of the product surface. The official OKF spec-check guidance adds another architectural boundary: embedded reference material and local validators support offline work by default, while fresh external specification checks are consulted only when needed and do not replace the local workflow unless the official spec has changed. The OKF quality baseline extends this by defining the expected internal shape of the wiki itself: reserved navigation files, concept documents with required frontmatter, tolerance rules for consumers, and stricter local checks for OpenKB-managed content. The OpenKB lifecycle reference adds a further operational layer: generated wiki pages, staged source copies, hash registries, machine-managed reports, and hand-authored tooling pages have distinct ownership and repair rules, so structure is tied directly to lifecycle boundaries rather than just file placement. The fallback skeleton generator adds a lower-bound architectural model for constrained environments: even without an LLM, the repository can still generate a minimal `okf/wiki/` with `concepts/`, `references/`, `index.md`, and `log.md`, seeded from repository metadata, Graphify output, and staged external docs. The README's air-gapped mode aligns with this lower bound by keeping the repository useful even when no remote LLM is available. The workflow reference turns that architecture into an explicit build order: read `okf/wiki/index.md` first when it exists, treat `tooling/index.md` as a routing surface only when the index sends you there, identify the active harness from runtime evidence rather than binary presence, run prerequisite checks before anything else, vendor required skills before CLI use, keep `okf/` out of the repo graph, preserve line-ending normalization, build staged input deterministically, disclose data flow before the first LLM-backed command, ingest staged inputs, validate, and then re-pass `AGENTS.md` so orientation stays aligned with the built wiki. The README mirrors that flow in product language by requiring consent-first installs, pinned versions, explicit data-flow disclosure, explicit provider routing, and a zero-LLM fallback when semantic compilation is not available. The subagent-profile-adapter skill extends this layered model into runtime-adapter generation: detect the active harness from runtime evidence, confirm whether it supports local subagents or profiles, and write native adapter files only after checking current harness docs. It treats adapter files as runtime-specific projections, not as a source of truth, and it requires that generated files stay short and point back to `AGENTS.md`, `okf/wiki/`, and relevant skills. The README matches that by describing harness adapters as native per-harness projections that should never become a source of truth. The tooling link policy validator refines that same architecture by making the tooling boundary explicit: tooling pages can describe or reference project pages, but project concept pages and subdirectory indexes must not create the reverse dependency, and the root `index.md` must surface tooling in a clearly labeled harness-specific section when local tooling pages are present. The README reinforces the same idea by calling out `tooling/` as a hand-authored exception that may be navigated from the wiki root but must not become a dependency source for project concepts. Together, those pages show documentation architecture as a controlled stack of orientation, context, actions, validation, and runtime projections.

The README adds an especially important framing detail: the repository itself is an example of the architecture it describes. It says the generated `AGENTS.md` and `okf/` knowledge base were written by the repository's own skills, and it distinguishes the three portable product skills from vendored toolchain copies. That makes documentation architecture recursive: the docs are both description and demonstration of the system. The same pattern appears in the managed `AGENTS.md` section, the compiled wiki, and the harness adapters, all of which are generated or maintained by the repository's own workflows rather than edited as one-off text dumps. In structural terms, that means architecture is not only a way to arrange documentation; it is also a way to produce it.

The README also makes the repository's navigation contract explicit. `AGENTS.md` is the front door for operational basics, `okf/wiki/` is the compiled knowledge base, `.agents/skills/` is the action layer, and harness adapters are local runtime projections. The concept pages and workflow references in this wiki align with that same order. `AGENTS.md` stays concise, the wiki carries durable context, and skills encode reusable procedures. That is a strong example of [[concepts/context-surface-management]], [[concepts/context-action-separation]], and [[concepts/progressive-disclosure]].

The merge script adds an especially important documentation-architecture detail: managed sections make it possible to keep canonical guidance synchronized without rewriting the whole file. By using start/end markers, the script can replace only the OpenKB-managed block, append it when missing, or create a new `AGENTS.md` when needed. That means the architecture can accommodate both local repository instructions and shared OKF routing guidance in one file without forcing a full overwrite. This is a good example of conservative document merging as a structural principle: preserve what is local and specific, update what is shared and managed, and keep the boundary visible.

The repository snapshot reinforces the same architectural picture from a different angle. The tracked-file inventory shows that the repository is organized around reusable agent skills and supporting policy material rather than application code alone. It includes dedicated skills for agent-ready context, Graphify, OpenKB, skill creation, and subagent profile adaptation, each with its own `references/`, `scripts/`, and `assets/` substructure. It also shows a small but important set of root-level governance files: `.gitattributes`, `.gitignore`, `.graphifyignore`, `AGENTS.md`, and `README.md`. That file mix suggests that documentation architecture is not incidental; it is one of the main organizing principles of the repository. The top-level image asset `docs/assets/agent-smith.svg` adds a small visual layer, but the dominant pattern is still documentary and workflow-oriented.

That makes documentation architecture here a question of both structure and boundary-setting. A document is valuable not only because it contains information, but because it clearly signals what kind of information belongs there, what should live somewhere else, whether it is authoritative, exploratory, procedural, generated, machine-managed, or external reference material, and how strictly it is expected to conform to local conventions. The Graphify report makes this especially concrete by showing both concentrated hubs and a large number of weakly connected fragments, which means structure is not only about where files exist but also about whether the relationships between them are legible. The skeleton generator makes this concrete by always separating overview pages from copied reference material and by warning that fallback-generated pages are navigable starting points rather than semantic truth. The merge script makes the same principle concrete inside `AGENTS.md`: it treats the file as a stable orientation surface with one managed section rather than a place where all durable context should accumulate. The agent-ready-context skill reinforces that separation by defining the skill layer as actions, the wiki as context, and `AGENTS.md` as orientation, with explicit rules for when to stage evidence, when to refresh the wiki, and when to validate. The workflow reference adds an operational reading order that reinforces the same layered model: `AGENTS.md` is not the start of truth; it is the project-facing front door, while `okf/wiki/index.md` is the first compiled knowledge surface and `tooling/index.md` is only consulted when the index routes there. The subagent-profile-adapter skill extends this same layering to runtime adapters, where harness-specific files are written only after runtime detection and docs review, and where the outputs are intentionally narrow projections rather than durable knowledge. The tooling link policy validator tightens the boundary by making directional linking itself part of architecture: local tooling pages are allowed to point outward, but compiled project pages must not depend on tooling context, and the root wiki index must preserve navigability by naming tooling explicitly when it exists. This aligns closely with [[concepts/agent-context-layering]], [[concepts/durable-context]], [[concepts/offline-first-workflows]], and [[concepts/spec-authority]].

## Main structural patterns
### Hub documents
A small number of files appear as central navigation points. The Graphify report makes this visible through both community hubs and god nodes: `README.md`, `AGENTS.md`, `OpenKB Wiki Schema`, `/graphify`, `What You Must Do When Invoked`, `OpenKB lifecycle for OKF maintenance`, and `OpenKB repo build workflow` dominate the graph. These documents and entry surfaces likely shape how contributors and agents orient themselves in the repository. The newer template and bootstrap evidence strengthen this pattern by defining `AGENTS.md` explicitly as a routing layer that points to other documentation systems rather than trying to contain all guidance itself. The OKF quality baseline adds that `index.md` and `log.md` are also special architectural hubs with reserved roles for navigation and history rather than general concept storage. The OpenKB lifecycle guidance refines this further by making `index.md` the normal read surface, while `log.md` remains machine-managed lifecycle history rather than a place for hand-written decisions. The workflow reference shows that `okf/wiki/index.md` is the first OKF page when it exists, with `tooling/index.md` read only when the index routes there. The fallback skeleton generator demonstrates that these hubs are important enough to be created even in the most conservative zero-LLM build path. The merge script adds that even within `AGENTS.md`, hub behavior is structured: one managed OpenKB section acts as a stable routing block while repository-specific guidance remains outside it. The agent-ready-context skill provides the same structural logic in prose by insisting that the repo's durable context source of truth is `okf/wiki/` and that the skill surface should not be used as a knowledge dump. The subagent-profile-adapter skill adds a runtime-specific hub behavior: tooling pages are allowed, but only as explicitly labeled harness-specific context, and the root index must point to them without letting project concept pages depend on them. The tooling link policy validator makes that hub behavior concrete by requiring root index navigation to tooling whenever the tooling subtree exists. The README strengthens this hub logic by defining the four repository surfaces as distinct roles rather than one undifferentiated documentation set.

### Layered documentation roles
The repository's guidance is divided into distinct documentation functions: human overview, agent instructions, durable knowledge, structural exploration, reusable procedures, embedded reference baselines, staged source evidence, machine-managed reports, harness-specific projections, and reserved navigation and history files. This division reduces ambiguity about where to place updates and makes the overall system easier to maintain as it grows. One of the clearest refinements from the newer sources is that generated wiki pages, raw ingested material, staged source copies, copied reference documents, harness adapter files, and hand-authored tooling pages are not interchangeable layers; each has different ownership and update rules. The Graphify report supports this layered reading by showing separate communities for README guidance, AGENTS guidance, OpenKB lifecycle material, skill creation, runtime detection, validation scripts, and Graphify references rather than one undifferentiated body of text. The skeleton generator reinforces this by separating synthesized overview pages in `concepts/` from copied evidence in `references/`. The merge script reinforces the same pattern by standardizing `AGENTS.md` as orientation and best-practice routing, `okf/wiki/` as durable context, Graphify as a structural aid, and skills as the home for recurring executable workflows. The workflow reference extends that same layering by placing deterministic staging before OpenKB ingestion, external URL materialization before ingestion, and data-flow disclosure before the first LLM-backed command. The agent-ready-context skill further formalizes this role split and makes `okf/.okf-build/` the staging area for deterministic input rather than a place for durable knowledge. The subagent-profile-adapter skill adds another layer: runtime adapter files are projections for the active harness only, not durable project knowledge, and they should stay short while pointing back to core context layers. The tooling policy validator adds a final nested layer: `okf/wiki/tooling/` is a local harness-specific context layer that may exist inside the wiki, but its links and navigation are directionally constrained so it cannot become a dependency source for project concepts. This pattern relates directly to [[concepts/agent-context-layering]], [[concepts/durable-context]], and [[concepts/skill-based-automation]]. The README adds an even cleaner high-level layer split: orientation, context, actions, validation, and runtime projection.

### Local coherence over global linkage
The report found no import cycles and no surprising cross-file connections. This suggests that documents are internally organized but not richly cross-connected across the repository. The AGENTS template and bootstrap guidance partially compensate for this by prescribing an explicit reading order and authority order, so architectural coherence comes from ordered navigation as much as from dense cross-linking. The OKF quality baseline adds a stronger OpenKB-specific expectation that `wikilinks` should resolve cleanly, which means local coherence is not only conceptual but machine-checked through stricter wiki linking rules. The OpenKB lifecycle guidance complements this by treating broken citation or registry relationships as architectural damage that should be repaired through recompile or remove-and-readd workflows rather than patched manually. The workflow reference reinforces this by making structure, staging, reconciliation, and ingest all precede any recompile so the KB's structural picture matches the code being recompiled against. ### Refreshable external authority
A newer pattern is the separation between durable embedded guidance and refreshable external standards. The official OKF spec-check workflow shows that repositories can remain operational offline while still preserving a path to re-check live standards when necessary. The merge script reinforces the same boundary by requiring external documentation to be materialized as evidence Markdown with URL, access date, and provenance, and by treating fetched content as untrusted data rather than instructions. The workflow reference adds that external URLs, when provided, should be materialized under `okf/.okf-build/input/external/` or added through `openkb add` with consent, and that provider flow must be disclosed before the first LLM-backed command. The README additionally presents official specs and related references up front while making the local repo's own wiki the durable source of truth. ### Reserved and validated page roles
A further structural pattern is that some filenames and directories are architectural roles, not just containers. The skeleton generator reinforces this principle by always creating `concepts/`, `references/`, `index.md`, and `log.md`, and by treating optional tooling context as an explicitly labeled outsider that concept pages must not depend on. The merge script adds a parallel reserved-role pattern inside a single file by using HTML markers to define a machine-managed `AGENTS.md` section whose boundaries are stable and whose contents can be refreshed without disturbing the rest of the file. The workflow reference adds that `.gitattributes`, `.graphifyignore`, `.gitignore`, `okf/.okf-build/`, and `okf/wiki/reports/` all have explicit roles in preserving staging and validation integrity. The tooling policy validator adds a complementary role system inside the wiki: `tooling/index.md` is a committed navigation stub, `index.md` and `log.md` are reserved navigation/history files, and tooling pages themselves are local harness context that should be reachable without leaking back into project concept links. The README adds that `AGENTS.md`, `okf/wiki/`, and `.agents/skills/` are the repository's core surfaces, while vendored `graphify` and `openkb` copies are deliberately excluded from the product role set. That means the repository's documentation architecture includes explicit differences between durable knowledge pages, operational evidence areas, machine-managed reporting areas, locally scoped tooling surfaces, and bounded managed sections in human-maintained orientation documents. This relates to [[concepts/evidence-staging]], [[concepts/durable-context]], and [[concepts/quality-gates]].

### Regeneration-oriented architecture
The new lifecycle guidance makes regeneration itself part of the architecture. Weak concept pages, duplicate names, vague summaries, or missing caveats are not meant to be corrected in place inside generated wiki output. Instead, the architecture directs maintainers back to committed source documents, git tracking, deterministic staging, and controlled recompilation. This means repository documentation is organized not only by reading layer but also by correction path: authoritative edits begin in source material and flow through staging, ingestion, summary generation, and validation. The fallback skeleton generator fits this pattern as the zero-LLM starting point for that pipeline: it seeds the wiki from git state, Graphify artifacts, and staged external files, but leaves semantic enrichment for later passes. The merge script extends regeneration thinking to `AGENTS.md` maintenance: rather than editing the orientation layer ad hoc each time, repositories can regenerate the standard OpenKB guidance block in place while preserving local instructions around it. The Graphify report supports this pattern indirectly by treating the graph as a freshness-sensitive artifact tied to a specific commit and recommending `graphify update .` after code changes. The workflow reference pushes the same logic earlier in the pipeline by insisting on deterministic source packs, deletion reconciliation, staged findings promotion, and post-generation review before accepting compiled output. The subagent-profile-adapter skill extends regeneration thinking to harness adapters: native files should be written from current docs, validated afterward, and kept small enough that future changes can be regenerated without hauling project context into the runtime projection. The tooling policy validator complements that by requiring root index and local stub coordination whenever tooling pages appear, so the navigation layer is regenerated as part of the same maintenance loop. The README brings this regeneration logic into the product story by emphasizing that the repository itself was transformed by its own skills and that local repository readiness is a repeatable lifecycle, not a one-time edit. That makes structural documentation itself part of a repeatable maintenance loop rather than a one-time snapshot. That pattern ties documentation layout directly to lifecycle safety and supports [[concepts/source-driven-regeneration]], [[concepts/evidence-staging]], and [[concepts/provenance-tracking]].

### Runtime-specific adapter layer
The subagent-profile-adapter skill introduces a distinct architectural layer for harness-specific runtime files. It says adapter generation should only happen when the current harness actually supports local subagents or profiles, and only after runtime detection rather than binary presence checks. It also asks how generated files should be tracked: local-only through `.git/info/exclude`, ignored through `.gitignore`, or committed as shared adapters. That means the architecture has to account for both the content of the adapter and the repository policy around its visibility. The skill further says adapter files should remain short and point back to `AGENTS.md`, `okf/wiki/`, and skills instead of inlining large amounts of repository context. It also insists that project concept pages never link back to tooling context, while the root wiki index must still surface tooling pages in a clearly labeled harness-specific section when they exist. This creates a careful separation between project truth and harness projection, while preserving navigation coherence at the bundle root. In documentation-architecture terms, that is a specialized form of runtime routing: the wiki describes the durable project, the skills encode repeatable actions, and the adapter file adapts that material to the active harness without becoming a third source of truth. The tooling policy validator gives this layer a precise link-direction rule so the routing surface remains explicit and the local tooling subtree stays local by default. That connects closely to [[concepts/runtime-adapter-management]], [[concepts/tooling-context-governance]], and [[concepts/link-directionality]]. The README makes the same point through its runtime-adapter and harness-specific framing, which keeps projection separate from source of truth.

## Why this concept matters
Good documentation architecture improves navigation, maintenance, and trust. In this case, the source documents suggest that the repository already has substantial documentation, but its structure may not fully expose relationships between topics unless readers understand the intended layer boundaries, authority boundaries, generation boundaries, and validation boundaries.

This has several practical implications:
- large hub documents can become overloaded
- important details may remain buried inside isolated sections
- policy and workflow guidance can dominate navigation
- weak cross-linking can make the documentation harder to traverse as a system
- unclear boundaries between instructions, evidence, generated outputs, procedures, navigation files, external references, and runtime adapters can make updates inconsistent
- hand-editing generated knowledge can break provenance and registry coherence even when the file tree still looks plausible
- fallback-generated pages can be mistaken for complete semantic coverage unless their provisional status is made explicit
- unmanaged edits to orientation files can blur the boundary between local repository guidance and reusable OpenKB workflow policy
- runtime adapter files can drift into project truth if they are not kept short, harness-specific, and explicitly subordinate to the wiki and skills
- inventory-heavy repositories can look organized while still hiding the functional distinction between skills, references, scripts, assets, configuration, and compiled knowledge surfaces
- a managed `AGENTS.md` section can be the difference between keeping shared routing current and accidentally overwriting local project instructions
- local tooling pages can become hidden dependencies if link direction is not enforced at the wiki boundary
- a root catalog that omits tooling when it exists can make a clone look complete while leaving local harness context undiscoverable
- a product README can accidentally blur the distinction between user-facing overview, repository operating model, and generated knowledge unless those surfaces are named explicitly

The newer bootstrap guidance makes one additional point especially clear: architecture is not only about document size or link density, but also about assigning authority and lifecycle. `AGENTS.md` provides orientation, the wiki preserves durable context, Graphify outputs support exploration, and skills encode repeatable actions. The Graphify report strengthens this by showing that these roles are visible in the actual repo structure as separate communities rather than merely aspirational categories. It also makes clear that the main opportunity is not hidden coupling in code, but uneven cohesion and weak integration across documentation surfaces. The official spec-check guidance adds that embedded baselines and local validators support normal offline operation, while official web sources provide periodic authoritative refresh when needed. The OKF quality baseline adds that even inside the wiki, architecture is enforced through page-type expectations, reserved filenames, and validation modes that distinguish strict local quality from baseline conformance. The OpenKB lifecycle reference adds that generated pages, raw storage, staged sources, reports, and registry state are coupled parts of one maintained system, so repair and improvement must follow the intended regeneration path rather than ad hoc editing. The skeleton generator adds that a minimal architecture still matters under constraint: even the fallback path preserves provenance cues, navigation, evidence separation, and tooling boundaries so later enrichment has a stable base. The merge script adds that orientation itself can be architected: a bounded managed section keeps standard workflow guidance current while preserving repository-specific setup and rules. The workflow reference extends that by making the build sequence explicit, with `okf/wiki/index.md` as the first OKF page, `tooling/index.md` as a routed exception, prereq checks before bootstrapping, vendored skills before CLI use, ignore rules for self-reference control, deterministic staging before ingest, and validation before acceptance. The subagent-profile-adapter skill extends the same logic to runtime adapters: detect the actual harness, ask how to track generated files, keep adapters short, and preserve a strict boundary between project knowledge and harness-specific projections. The tooling link policy validator makes that boundary operational by allowing tooling to exist as a local harness layer while preventing the compiled project wiki from becoming dependent on it. The repository snapshot makes the architecture concrete at the file level, showing that the repo's tracked surface is already organized around these layered roles rather than a single undifferentiated documentation space.

These concerns connect closely to [[concepts/quality-gates]], [[concepts/provenance-tracking]], [[concepts/tooling-consent-and-pin-management]], and [[concepts/source-trust-levels]], because documentation structure affects how easy it is to validate content, trace where guidance comes from, manage generated versus durable artifacts, and decide when local references or external authorities should control a workflow.
