# Quality Gates

Quality gates are the checks, standards, review steps, approval boundaries, and validation commands used to keep a repository's outputs reliable, reproducible, and fit for downstream use. In this wiki, the concept spans structural validation of generated knowledge artifacts, workflow rules for when agents may build or ingest, and the approval boundaries around installs, provider-backed actions, and destructive maintenance. It includes dependency readiness, consent-first bootstrap decisions, exact version pinning, integrity verification for local tools, provider disclosure before model-backed commands, CI-facing enforcement that can block invalid OKF changes, and advisory health reporting that stays outside the merge gate. It also includes the OpenKB lifecycle discipline around read-first inspection, staged ingestion, deterministic recompile, hash-registry coherence, and the rule that wiki content is derived data, not operating instructions. The source-pack builder expands this concept by making staging itself deterministic: it inventories tracked files, filters out transient paths, records the last commit that touched each source, normalizes line endings, avoids embedding HEAD, and writes a manifest so staged bytes stay stable across runs. The editorial curation pass adds a final guardrail for manual knowledge-base maintenance by making class-3 merges and splits safe to perform only after a briefing and a deterministic diff check against the installed OpenKB tooling.

## Why This Matters

Quality gates reduce the risk of drift, malformed outputs, broken links, silent deduplication errors, weakly grounded summaries, undocumented tooling changes, unsafe dependency installs, undisclosed provider routing, stale graph recompiles, self-referential graph pollution, and registry/wiki mismatches that can leave knowledge permanently missing until explicitly repaired. In the structural view captured by [[summaries/graphify-report]], quality-related material appears as a central organizing concern rather than a minor supporting detail.

The source-pack builder reinforces that same concern by making repository staging reproducible and traceable instead of ad hoc: unchanged tracked files produce stable staged bytes, staged file names can optionally include hash prefixes, and the manifest records enough provenance to compare a staged document back to its source path and commit.

The newer agent-ready template reinforces that validation is not only a technical check but also an operational discipline: agents are expected to inspect status before ingesting, ask before expensive or destructive actions, review generated wiki changes, and validate the final wiki before finishing. The bootstrap reference adds another dimension by showing that tooling itself must pass through quality gates: prereqs are checked with an executable readiness script, companion skills are optional rather than hard blockers, and installs are consent-first, pinned, and tied to verified upstream sources. The prereq script itself adds concrete operational expectations: it distinguishes hard requirements from optional accelerators, checks repository writability by creating and deleting probe files, reports degraded mode when bare `python3` is used instead of `uv`, and surfaces missing companion skills as capability notes rather than hard failures. The lifecycle reference adds a maintenance-specific layer: agents should read `status` and `list` first, prefer `recompile` and staged `add` over direct edits, treat `okf/raw/` and generated wiki pages as owned output, and handle `lint`, `lint --fix`, `query --save`, `visualize`, external URL fetches, and destructive cleanup as consent-sensitive operations. It also adds a crucial failure mode: if the hash registry still claims a document is ingested after its generated pages are lost, future adds can silently skip the content, so post-merge lint review and explicit repair steps are part of quality control rather than optional housekeeping. The provider configuration reference adds a parallel gate for model-backed work: model choice should be explicit, credential resolution should be understood, and the operator should disclose tool, provider, model, endpoint, credential source, and the content being sent before the first add, recompile, lint, query, chat, skill, or deck action that reaches an external model. The workflow reference adds that quality also depends on build order and structural exclusion rules: Graphify should run before source-pack creation when available, the source pack should be rebuilt before any recompile, generated wiki changes should always pass through review and validation after `add` or `recompile`, `.graphifyignore` must exclude `okf/`, and the KB must never become input to the graph pipeline that later feeds the KB again. The validator summary sharpens the same theme by showing that even within structural validation the repository distinguishes hard errors from warnings, and can optionally promote warnings to errors when stricter enforcement is needed. The CI validation workflow adds a further layer by showing how the same discipline can be enforced automatically on pull requests that touch `okf/**`.

The OKF quality baseline adds an important framing rule: some checks define what a conformant bundle must satisfy, while others are repository quality bars chosen by producers. That distinction matters because it prevents the repository from confusing interoperability requirements with local enforcement preferences. A bundle may still be tolerated by consumers even if optional metadata is missing or standard Markdown links are broken, while the same repository may still choose to fail local validation for OpenKB-specific damage such as broken wikilinks, missing machine-managed `sources:` fields, malformed reserved files, evidence of truncated pages, or registry drift that can no longer heal through ordinary ingest. Together, these sources expand quality gates from simple output checks into a broader repository control system spanning local workflow, repository policy, dependency management, provider configuration, lifecycle repair discipline, automated enforcement, deterministic staging, executable readiness, build ordering, and spec-aware tolerance boundaries. The source-pack builder extends that control system into the staging layer itself by making file selection, file grouping, file splitting, and last-touch provenance part of the same deterministic pipeline. The editorial curation pass adds a distinct maintenance gate: it lets an agent perform a documented last-resort hand edit only after loading a briefing that mirrors the vendor's own wikilink whitelist, then verifies the resulting diff with public OpenKB lint APIs plus git-based scope and provenance rules.

## What Quality Gates Cover

Based on the source material, quality gates in this repository include several kinds of control:

### Structural Conformance

Checks ensure that bundles and generated outputs follow expected structure. The graph report points to concerns such as bundle structure, concept documents, index files, log files, and links and citations. The agent template adds an explicit requirement to validate OKF output with `validate_okf_bundle.py`, showing that structure is enforced through a named validation step rather than left to manual inspection. The CI workflow sharpens this further by demonstrating a pull-request job that runs the same validator against `okf/wiki` with an OpenKB-specific flag, making structural conformance a machine-enforced merge condition. The OKF quality reference makes the baseline explicit: every non-reserved `.md` file must have parseable YAML frontmatter and a non-empty `type`, while reserved `index.md` and `log.md` must follow their reserved structures when present. The validator summary adds finer points to that baseline: root `index.md` may carry frontmatter only to declare `okf_version`, non-root reserved `index.md` files must not have frontmatter, and `log.md` date headings are checked for the expected ISO-like structure. It also treats empty or weakly structured reserved pages as warnings rather than always escalating to hard failures, preserving a distinction between conformance and local quality policy. The lifecycle reference adds that generated wiki pages, raw copies, and the dedupe registry must remain coherent after merges, reverts, and recompiles, so structural conformance is about tree shape and lifecycle state, not just page formatting. It also adds that `okf/wiki/AGENTS.md` is a supported conventions file while `okf/wiki/log.md` remains OpenKB-managed, making reserved ownership rules part of structural quality. The workflow reference adds that the build path itself has structural prerequisites: the target repository must be Git-backed before source-pack creation, `.gitignore` must exclude build outputs and caches, `.graphifyignore` must keep `okf/` out of the graph, and `okf/wiki/AGENTS.md` should be re-merged and inspected after generation. The prereq checker adds one more concrete layer by verifying writable access to `.okf-build/input`, `okf`, and `.agents/skills`, treating unwritable required paths as hard failures before structural build steps even begin. The source-pack builder contributes a companion structural rule: oversize content is split into deterministic parts at prose headings or code layout boundaries, or bundled by path prefix, so the staged input remains complete without truncation. This is closely aligned with [[concepts/deterministic-validation]] and [[concepts/filesystem-validation]]. The editorial pass script adds a structural curation rule: only `concepts/`, `entities/`, and the root `index.md` may change, and any new compiled page must be explicitly allowed before it can enter the pass.

### Link and Reference Integrity

The presence of validation tooling and explicit policy communities suggests that internal references, including wikilinks and tooling links, are expected to resolve correctly. The broader workflow also expects generated pages to be checked for duplicates, vague naming, misplaced entity or concept pages, and proper grounding through citation chains. The OKF quality baseline clarifies that standard Markdown links may remain broken without breaking conformance, because consumers should tolerate partially generated knowledge. OpenKB-managed wikilinks are treated differently: broken ones are errors because they indicate damage relative to a compile-time whitelist and are repairable by repository tooling. The validator summary clarifies how this works in practice: every Markdown file contributes valid targets through both its wiki-relative path and bare stem, link aliases are stripped before comparison, and code spans or fenced examples are ignored during scanning so documentation can discuss link syntax without generating false failures. The lifecycle reference deepens this by describing a deterministic citation chain from concept or entity page to summary, staged source copy, and original repository file or URL, and by treating empty or missing machine-managed `sources:` metadata as a sign of damage to be repaired through recompilation rather than hand edits. It also notes that early-compiled pages can become stale in link structure because they only saw the wiki state available at compile time, so targeted recompilation is a quality repair for order-dependent staleness as well as missing content. The workflow reference adds a practical review checklist after `add` or `recompile`: inspect each changed page for near-duplicates, missing or vague concepts, lost caveats, truncation, stale early pages, and grounding back through staged sources and commit history. This connects quality gates closely with [[concepts/documentation-architecture]], [[concepts/knowledge-linking-and-citations]], [[concepts/caveat-preservation]], and [[concepts/wikilink-integrity]]. The source-pack builder supports the same integrity model by tying each staged item back to a manifest entry and a last-touch commit rather than to a mutable build-time HEAD stamp. The editorial pass script applies the same link-integrity concern at the point of curation: it loads the current complete wikilink whitelist, allows only explicitly approved new page slugs, and warns if the private vendor template cannot be used verbatim.

### Reproducibility

The graph report shows build-oriented communities that emphasize stable outputs, normalization, and git-aware processing. Examples from the graph include logic for dropping run-dependent lines and mapping paths to the latest touching commit. The agent template sharpens this by requiring deterministic construction of `.okf-build/input/`, cautious handling of recompile operations, and review of generated changes before acceptance. The bootstrap reference extends this logic to local tooling: bundled scripts are expected to run through `uv run`, readiness is re-checked after installs, and pinned tool versions are recorded rather than floated casually. The CI validator adds a reproducible check path that can be rerun in a standard environment on every pull request. The OKF quality reference supports this by providing an embedded offline baseline, so validation can still be performed consistently even when network access is unavailable. The validator summary adds that the script is intentionally OS-agnostic, uses `pathlib` and recursive Markdown discovery instead of shell-specific behavior, normalizes line endings while reading frontmatter boundaries, and reports a consistent pass/fail result with optional strict-warning escalation. The lifecycle reference adds that staging alone does not update `okf/raw/` or `okf/wiki`, that repeated ingest is controlled by hash deduplication, and that reproducibility depends on understanding when source rebuilds, `add`, and `recompile` actually change the generated state. It also notes that large repositories may need bundled staging rather than per-file staging, and that switching bundle strategy later re-hashes the whole staged pack and triggers broad re-ingest. The workflow reference makes this more concrete by requiring a specific refresh order: rerun Graphify when installed, rebuild the source pack, ingest with `openkb add`, preview regeneration with `recompile --dry-run`, and only then review and validate. It also explains that each staged file should record the last commit that touched that file rather than repository `HEAD`, so unchanged files remain byte-identical across commits and dedupe remains effective. The workflow also adds a reproducibility boundary around graph scope: a graph report that includes `okf/` is rejected because self-reference would cause the report to mutate whenever the wiki changes. The prereq checker contributes an executable reproducibility boundary by requiring Python 3.11+ and validating tool presence up front, reducing ambiguity about which runtime and command surface the workflow is actually using. The provider configuration reference adds that reproducibility also depends on explicit model naming, known credential precedence, and stable provider selection rather than opportunistic use of whatever environment happens to be active. A valid output is therefore not just correct once, but stable across repeated runs when inputs, provider choice, graph scope, and toolchain expectations have not meaningfully changed. The source-pack builder embodies that reproducibility at the file level by normalizing text before hashing and by making selection, bundling, and splitting deterministic. The editorial pass script contributes a different kind of reproducibility by rendering the same whitelist briefing from either the live private template or a mirrored fallback and by making `--check` a zero-LLM validation pass over the current diff.

### Provenance and Trust

Quality gates also support traceability. The graph connects validation and build workflow material with provenance-oriented concerns, making this concept closely related to [[concepts/provenance-tracking]]. The agent template adds that external documentation should be materialized as evidence with URL, timestamp, and provenance, and that generated knowledge should remain traceable to source commits and external URLs. The bootstrap reference adds the same logic for tools: every installable dependency should have an authoritative upstream source, exact package identity should be verified, and older conflicting install guidance should be treated as suspect rather than copied forward. The lifecycle reference contributes a detailed provenance chain: generated concepts and entities point to summaries, summaries point to staged source copies, and staged sources record `source_path`, `source_hash`, and `source_commit`. It also notes that staging outside `okf/` can leak absolute host paths into registry metadata, turning provenance into a privacy concern as well as a traceability feature. The workflow reference strengthens this by requiring external URLs to be materialized under `.okf-build/input/external/` or added through user-approved commands, preserving URLs and timestamps, and treating fetched content as evidence rather than instructions. It also states that repo snippets should stay short and that credentials must never appear in evidence files, generated pages, `AGENTS.md`, or committed config. The OKF quality reference contributes a spec-authority rule: when web access is available, the embedded baseline should be refreshed against the official OKF spec and README, and the official documents win if they differ. The validator summary reinforces trust through transparency of enforcement: when PyYAML is absent the script does not silently skip frontmatter validation, but emits an explicit error that YAML parseability cannot be confirmed locally. The prereq checker adds trust-oriented diagnostics for local tool presence and install posture: it treats `uv` as a required prerequisite, gives explicit install guidance when absent, and frames optional tools such as Graphify and `openkb` with named package identities and upstream sources rather than vague commands. The provider configuration reference adds another trust boundary: provider routing should be disclosed before staged content is sent, credential source should be understood, and cloud OCR or model services should be recognized as provenance-relevant transformations rather than invisible plumbing. The source-pack builder contributes provenance at the staging boundary by naming the source commit that last touched each file and by making the manifest a durable record of staged selection, hashing, and part counts. The editorial pass script adds provenance protection at edit time by requiring that the union of `sources:` values across concepts and entities remain unchanged unless a split or merge has been explicitly approved.

A repository can only enforce meaningful quality if it can also show where both its artifacts and its supporting tools came from, how they were produced, which provider processed them, and which authority defines the current validation rules. This ties quality gates to [[concepts/source-trust-levels]] and [[concepts/spec-authority]].

### Workflow Safety and Approval Boundaries

The newer document makes clear that some quality gates are procedural rather than purely technical. Agents should confirm prerequisites, obtain consent before installing tooling, ask before expensive or destructive operations such as `remove`, `recompile`, `lint`, `lint --fix`, `query --save`, and `visualize`, and prefer dry-runs before destructive actions. The bootstrap reference makes this procedural layer even more explicit: bootstrap is consent-first, each missing tool should be presented with its purpose, package name, registry, upstream source, pinned version, and exact command, and the user should choose whether to install it, have it installed for them, or skip it. The prereq checker sharpens this distinction by separating hard failures from missing optional capabilities and by turning skipped companion skills into explicit notes rather than silent absences. The lifecycle reference strengthens this by explicitly treating some commands as model-backed disclosures, warning against autonomous `watch` or `chat` sessions, requiring that external URL ingestion only happen after clear user consent and data-flow explanation, and recommending `status` and `list` as read-first preflight checks before more invasive work. It also treats `remove --dry-run` and `recompile --dry-run` as normal safety posture, with broad refresh actions such as `--all` or `--refresh-schema` reserved for explicit approval. The workflow reference sharpens these approval boundaries further by requiring consent before bootstrapping hard prerequisites, optional tools, Git initialization in non-Git directories, CI installation, and local hooks, while also forbidding broad `recompile --all` without consent. It treats post-generation review as a required acceptance gate rather than a nice-to-have, and requires disclosure before the first provider-backed OpenKB operation. The provider reference sharpens this boundary further by requiring explicit disclosure before the first provider-backed OpenKB operation, including provider, model, endpoint, credential source, and what content will be transmitted. It also warns against assuming the active harness is the billing or policy target the user wants. These approval boundaries function as quality gates because they prevent low-visibility changes and low-visibility data transfers from entering the repository workflow without review. The validator summary adds a quieter but important approval pattern: warning-only findings can remain advisory until local policy chooses to activate `--strict-warnings`, which makes escalation itself an intentional governance choice. The CI template contributes a related governance pattern: installation is framed as intentional repository setup rather than assumed by default, and action pinning is left adjustable to local policy. The source-pack builder contributes a related safety boundary by refusing to stage graph reports that would pull compiled wiki paths back into the next ingest cycle. The editorial pass script adds a maintenance-specific approval boundary by allowing new compiled pages only if they are explicitly listed in `--allow-new-pages`.

### Dependency Readiness and Tool Boundaries

The bootstrap reference adds a major expansion of this concept: tool readiness itself is gated. `check_prereqs.py` is the executable source of truth for whether the local environment is fit to proceed, while `allowed-tools` remains only a hint about harness capabilities rather than an install manifest or enforcement mechanism. The prereq script now makes that role concrete by checking Python 3.11+, `git`, `uv`, Git worktree membership, optional Graphify and `openkb` CLIs, companion skill presence, and repository writability, then returning either machine-readable JSON or grouped terminal diagnostics. It also uses resolved executable paths to avoid Windows shim problems and ASCII status markers for console compatibility, which turns cross-platform reliability into part of the gate itself. The document also distinguishes harness tools from local CLIs, warning that repository workflows should not confuse shell or file-edit access provided by the agent environment with installed commands like `git`, `python`, `openkb`, or `uv`. The workflow reference reinforces this separation by making `check_prereqs.py` the first step in the decision tree, requiring bundled scripts to run through `uv run`, and allowing fallback to `python3` only when the user explicitly declines `uv`, with degraded mode reported. It also adds a companion-skill boundary: when Graphify or `openkb` will run, pinned vendored copies under `.agents/skills/graphify/` and `.agents/skills/openkb/` must exist first, and the workflow must not proceed while that prerequisite is flagged as missing. The validator summary adds a related runtime boundary: the validator can run with bare `python3`, but YAML validation degrades when PyYAML is absent, so the repository treats `uv run` as the preferred execution path for consistent results. The OKF quality baseline adds a related boundary inside the wiki itself: `tooling/` is valid under OKF as a normal grouping, but this repository imposes a stricter semantic separation in which tooling pages may link into project context while project concept pages must not depend on tooling context. The lifecycle reference adds that `okf/wiki/tooling/` and approved `okf/wiki/AGENTS.md` conventions are the narrow hand-authored exceptions inside an otherwise generated tree, which makes quality partly about respecting ownership boundaries between source material, generated knowledge, and operator-authored conventions. The provider reference adds a parallel runtime boundary: credentials can come from several scopes, local models differ from cloud providers, and commands that appear similar can have very different external data paths depending on the configured litellm model name. This makes quality gates partly about enforcing clear operational and documentation boundaries, closely tied to [[concepts/tool-boundaries]], [[concepts/dependency-management]], [[concepts/cross-platform-tooling]], [[concepts/skill-vendoring]], and [[concepts/provider-integration]]. The editorial pass script uses the installed OpenKB toolchain directly for both the public lint API and the private whitelist template when possible, and treats a missing installed `openkb` venv as an environment failure rather than silently substituting a different implementation.

### Supply-Chain Integrity and Pinning

The bootstrap reference also shows that repository quality includes controlling the trust surface of local tooling. Exact versions must be pinned in commands left behind, installs must respect the configured Python index rather than bypassing mirrors, and recorded hashes must anchor trust-on-first-use integrity checks for later machine bootstraps. A mismatch for the same version and index is treated as a stop-and-report event rather than something to silently repair. The prereq checker supports this policy indirectly by refusing to treat missing hard prerequisites as invisible setup details: if `uv` is absent, the script records the failure and instructs the operator to install it from the documented source rather than normalizing ad hoc fallback. It does the same for optional tools by naming package and upstream source while still preserving [[concepts/graceful-degradation]]. The workflow reference contributes another integrity control at the repository-content layer: `.gitattributes` should be installed or merged from the provided template so line-ending policy remains explicit and deterministic. If an existing normalization rule conflicts with the template, the user must be shown both versions and asked; silent override is disallowed. After changes, `git add --renormalize .` is recommended so normalization rules and content hashes align. The workflow also adds that `.gitignore` and `.graphifyignore` are part of the trust surface because they control which generated state, caches, secrets, and graph scope boundaries enter reproducible processing. The provider reference adds an adjacent trust surface for model access: the selected provider path, endpoint conventions, and credential source should be explicit, and cloud add-ons such as PageIndex should be treated as meaningful external dependencies rather than transparent defaults. The lifecycle reference adds that the hash registry itself is part of the trust surface: when it disagrees with raw or generated state, the right response is explicit repair through `recompile` or `remove` plus re-add, not silent manual patching. These rules turn package provenance, mirror discipline, provider routing, line-ending policy, registry coherence, recorded integrity, and graph-scope configuration into first-class quality controls, directly reinforcing [[concepts/supply-chain-security]], [[concepts/tooling-consent-and-pin-management]], [[concepts/git-attributes]], and [[concepts/line-ending-normalization]]. The source-pack builder complements this by basing provenance on Git history rather than mutable build-time state, so staging remains aligned with the repository's trust record.

### Source-Driven Correction

The template also defines a correction loop: weak generated pages should be fixed by improving source documents and re-ingesting rather than by directly editing generated wiki pages. The lifecycle reference makes that principle more concrete by stating that the durable fix for weak concept names, missing foundational ideas, misfiled entities, flattened caveats, or near-duplicates is to improve committed source material under the repository's normal docs or code surfaces, ensure it is git-tracked, rebuild staging, re-add sources, and recompile affected documents. It also explicitly warns that hand edits to generated wiki pages will be overwritten and can desynchronize the wiki from the hash registry. The same rule applies to example and fixture content: if a sample file compiles into misleading project concepts, the source example should be rewritten or clarified, then re-ingested and previewed with dry-runs rather than silently excluded or patched in the output. The workflow reference makes this a formal review rule: every finding from the post-generation pass should go through the correction loop of fixing source docs, re-ingesting, and recompiling, never hand-editing generated pages. It also adds that off-topic distillate from examples, stale early pages from interrupted ingestion order, and broken grounding chains are all review findings to resolve through the same source-driven path. The validator summary reinforces the same pattern indirectly by treating unclosed fences and slug-collision warnings as likely symptoms of truncation, bad merges, or source-shaping problems that should be repaired at the generating layer rather than patched in place. The provider reference indirectly supports the same pattern by recommending cheap read-only checks and a small single-file add before broader ingestion, which creates a controlled correction loop before costly or wide-scope model-backed processing. The source-pack builder extends this principle by ensuring that rebuilds are derived from tracked source files and that oversized content is preserved in split parts rather than cropped away. That makes quality gating part of a larger regeneration discipline, closely tied to [[concepts/source-driven-regeneration]]. The editorial pass script reinforces the same correction loop for manual maintenance by making its `--check` mode deterministic, zero-LLM, and scoped to the curation diff.

### Deterministic Versus Advisory Checks

The CI workflow makes an important distinction within quality gating itself: structural validation is suitable for failing CI because it is deterministic, zero-LLM, and exits nonzero on violations, while `openkb lint` is explicitly excluded because it is an advisory health report that always completes without failing the build. The bootstrap reference complements this distinction by separating hard requirements from optional companion tools and by allowing degraded execution when a user explicitly declines `uv`. The prereq checker follows the same model by separating required tools and writable paths from optional tools and companion skills, then collecting explanatory notes instead of collapsing every missing component into one failure class. The lifecycle reference sharpens the same split: `openkb lint` writes findings to reports and still completes even when its knowledge-lint half cannot run, while the structural validator is the pass/fail gate for CI and hooks. It also notes that `lint --fix` is deterministic link rewriting followed by the same reporting pipeline, so even remediation has a different governance role from pure validation. The workflow reference reinforces the division by describing `validate_okf_bundle.py` as the only pipeline component that both needs no LLM and fails on violations, making it the right target for CI and local hooks. It also explicitly says `openkb lint` does not belong in CI or hooks because it is LLM-backed and non-blocking. The validator summary gives this distinction sharper detail: errors cover conformance failures and broken OpenKB wikilinks, warnings cover softer quality issues like empty bodies, missing recommended fields, unclosed fences, or same-directory slug collisions, and `--strict-warnings` provides an opt-in path for promoting advisory findings into hard gates. The OKF quality baseline formalizes the same split by separating hard conformance rules from producer-side quality checks: missing optional frontmatter, unknown `type` values, broken standard Markdown links, and missing `index.md` files are not reasons to reject a bundle, while OpenKB-specific checks such as broken wikilinks, unclosed code fences, or same-directory slug collisions can still be treated as repository-quality findings. The provider reference adds another practical split: `status` and `list` are cheap read-only preflight checks, while add, recompile, lint, query, chat, skill, and deck may trigger model-backed flows and therefore require disclosure and tighter review. The source-pack builder makes a similar distinction at the staging layer by separating the immutable inventory snapshot from the content-bearing repo-file documents and by keeping the graph report optional, not mandatory. Not every useful check or tool should serve the same enforcement role. Some checks are hard gates, while others are diagnostic aids, preflight checks, or optional accelerators. In this repository, the split helps preserve both strict conformance enforcement and careful local analysis, tying quality gates to [[concepts/deterministic-validation]] and [[concepts/privacy-preserving-tooling]]. The editorial pass script fits this pattern by separating its human-facing briefing from its deterministic post-edit check and by falling back only in wording, not in verification.

## Structural Role in the Repository

In [[summaries/graphify-report]], quality gating appears as part of the repository's backbone. The graph's most connected nodes include both explicit validation topics and workflow documents that describe when and how checks should happen. This suggests a workflow in which quality gates are embedded early and repeatedly rather than applied only at the end.

The new agent template strengthens that reading. It places checks at multiple stages: before tooling bootstrap, before ingestion, before expensive operations, during generated-page review, after merges or reverts touching `okf/`, and at final validation. The bootstrap reference deepens the same pattern by placing gates even earlier, at environment readiness and installation time: before the workflow can run confidently, the repo should know whether required tools exist, whether optional tools are being skipped intentionally, whether the package source is legitimate, and whether version and integrity expectations are recorded. The prereq script makes this structural role executable by providing a single readiness report that can fail early on missing hard requirements while still preserving notes about optional gaps and companion-skill absences. The CI validation workflow adds a repository-hosted checkpoint at pull-request time, specifically scoped to changes under `okf/**`, showing that quality enforcement can be targeted to the artifact boundary that matters most. The lifecycle reference adds a crucial integrity warning: `okf/.openkb/hashes.json` and `okf/wiki/` form a single quality unit, since a preserved dedupe registry paired with lost wiki pages can cause future adds to skip content silently. That is a repository-level quality concern, not just an implementation detail. It also explains why the lifecycle starts with `status` and `list`: state inspection is part of the gate, not merely a convenience.

The workflow reference adds a similarly structural pattern for repository compilation. It requires `.gitignore` coverage for build outputs and caches, explicit `.gitattributes` normalization rules for stable staging, `.graphifyignore` exclusion of `okf/`, Git history before source-pack creation, Graphify refresh before ingestion, and a post-generation review loop before final acceptance. It also recommends rerunning validation after merges of `AGENTS.md` content back into `okf/wiki/AGENTS.md`, which treats local policy overlays as part of the quality surface rather than as separate administrative material. Just as importantly, it defines self-reference control as a structural quality rule rather than an aesthetic preference: the wiki stays out of the graph so deterministic builds, grounding chains, and discovery quality remain intact. The source-pack builder makes this structural role concrete by ensuring that the build pack itself is a stable, manifest-backed boundary between the Git repository and OpenKB ingestion. The editorial pass script extends that boundary by acting as the last sanctioned manual editing corridor before the compiled wiki changes are validated.

The OKF quality reference adds a structural backbone for these practices. It defines the expected local layout under `okf/wiki/`, confirms that `index.md` and `log.md` are reserved at any level, and documents how OpenKB validation intentionally skips operational or policy-specific areas such as `sources/`, `reports/`, and the root `AGENTS.md` while still validating the main knowledge-bearing areas. The validator summary sharpens that picture by noting that skipped operational files may still contribute valid wikilink targets, so navigation integrity is checked against the whole repository shape even when only part of the tree is treated as concept content. It also explains why root `index.md` receives special handling while other reserved files remain tightly constrained. The lifecycle reference complements this by describing `okf/wiki/AGENTS.md` as the supported extension point for local conventions, `okf/wiki/tooling/` as the hand-authored exception area, and `log.md` as machine-managed rather than a place for manual decisions. The provider reference extends the same model into external execution paths by showing that quality checks begin before content leaves the repository boundary: the chosen provider, model family, endpoint style, local-versus-cloud processing path, and credential scope all affect what kind of review is needed before an OpenKB command is considered safe to run. The lifecycle reference also adds that order matters: a page compiled early can become stale against the later wiki state and may need `recompile` to repair its links and citations after new concepts appear.

The concept also helps explain why some tooling files are prominent community hubs. Validation scripts, baseline documents, dependency guidance, provider configuration references, workflow guides, evidence-handling rules, and prereq diagnostics act as coordination points between repository policy, generated artifacts, provenance discipline, external data handling, and operational maintenance. The CI template is part of that same pattern: even as a small file, it encodes decisions about what should block merges, what should remain local, and how strongly the repository should prefer deterministic checks over advisory analysis. The bootstrap reference does similar work for local setup by encoding what counts as a trustworthy install, what degrades gracefully, and what should cause the workflow to stop and ask. The prereq checker adds a concrete enforcement surface for those expectations by turning them into a repeatable command with stable exit behavior. The workflow reference adds the ordering discipline that determines when structural context is fresh enough to justify ingestion or recompilation. The validator script adds the executable semantics of the gate itself: concept pages, reserved files, operational exclusions, warning classes, and broken-link handling are all encoded in one place rather than left implicit. The provider reference adds disclosure and model-selection rules that determine when a command changes from a local maintenance step into an outbound data-transfer event. The lifecycle reference adds the operational memory of how generated state is safely maintained over time, especially when deduplication, recompilation, citation-chain repair, order-dependent staleness, provider-backed actions, and self-reference control are involved. The source-pack builder contributes the staging memory: bundle hashes, part hashes, manifest entries, and per-file source commits. The editorial pass script adds a curation-memory layer by rendering the vendor whitelist briefing and by checking the curation diff against the installed OpenKB APIs rather than a handwritten approximation.

## Observations and Implications

The combined evidence suggests that quality gates in this repo are not limited to a final validator script. They span repository structure, build determinism, provenance capture, consent-based tooling changes, dependency readiness, supply-chain checks, provider selection, data-flow disclosure, review of generated outputs, filesystem readiness, protection against silent state mismatches in the knowledge base, graph-scope controls, deterministic source-pack staging, and a documented manual curation escape hatch that still remains machine-verifiable. The CI workflow makes this broader picture more concrete by showing exactly which kind of check is strong enough to gate merges: deterministic structural validation, not advisory analysis. The bootstrap reference adds the equally important point that a workflow cannot be considered high-quality if it relies on unclear package identity, unverified mirrors, floating installs, or hidden bootstrap assumptions. The prereq checker adds a complementary point: a workflow is also lower-quality if it assumes writable paths, Git worktree context, or local CLI availability without checking them first. The provider reference adds that a workflow is also lower-quality when it hides which external model or OCR service will receive staged content, or when credential precedence and endpoint choice are left implicit. The lifecycle reference adds that a workflow is also low-quality if it ignores hash-based deduplication semantics, edits generated pages by hand, skips read-first inspection before KB changes, or fails to inspect lint findings after merges touching `okf/`. The workflow reference adds a final operational warning: even structurally valid outputs can still be poor if they were generated from a stale graph, accepted without review, compiled from evidence that was not staged and preserved with provenance, or allowed to feed the KB back into the graph that then shapes the next ingest. The validator summary adds one more implication: structural validity itself has layers, from hard frontmatter and reserved-file rules to softer but still meaningful signs of damage such as unclosed fences, empty bodies, and near-duplicate page names. The editorial pass script shows that these layers extend into manual curation too: a safe edit depends on the right installed OpenKB environment, the right whitelist briefing, a constrained scope, and a deterministic diff check before the curation is accepted.

The OKF quality baseline adds a useful conceptual discipline: not every failure mode belongs to the same layer. Some issues are hard spec violations, some are OpenKB convention violations, some are local semantic policy violations such as project-to-tooling link direction, some are environment-readiness failures, some are lifecycle coherence failures between registry and generated pages, some are graph-scope failures caused by self-reference, and some are outbound execution risks that require disclosure and user choice rather than structural rejection. This layered model helps the repository enforce strong guarantees without overstating what the underlying format requires. It also clarifies why some warnings should remain warnings: unknown frontmatter keys, unknown `type` values, and missing optional metadata are part of a tolerant ecosystem even when stricter local pages or templates prefer more structure. The lifecycle reference extends that layering into operations by separating hard validation gates from advisory health reports, by distinguishing repair actions that regenerate from approved sources from edits that merely patch symptoms, and by showing that some state problems persist until explicitly repaired. The prereq checker extends the same layering into bootstrap by distinguishing missing hard requirements from optional tools and companion skills. The provider reference extends the same layering into runtime behavior by separating harmless read-only checks from commands that may route content to a cloud provider. The workflow reference complements this by distinguishing deterministic gates from review-only safeguards: some failures belong in validators, while others belong in the post-generation human or agent review pass. The validator script gives this layered model executable form through separate error and warning channels plus an optional switch for stricter local enforcement. The source-pack builder adds another axis: full-content parts versus bundles versus one-file staging are all quality-preserving representations of the same source, chosen to balance determinism, completeness, and scale. The editorial pass script adds a parallel distinction between live vendor middleware and a mirrored fallback: the former is preferred, but the latter preserves briefing continuity without changing enforcement.

The graph report suggests that quality gates are well represented in major repository hubs, but it also reveals many weakly connected nodes elsewhere in the graph. That matters because isolated components may indicate places where validation logic, policy coverage, documentation links, or prereq expectations are incomplete. The agent template adds a similar concern in operational form: generated pages may pass through the pipeline yet still be poor if they contain duplicate concepts, weak names, lost caveats, or thin citation grounding. The bootstrap reference adds another operational warning: optional tools and companion skills should not be treated as hard failures, because [[concepts/graceful-degradation]] is itself part of a well-designed quality regime. The prereq checker embodies that principle directly by preserving usability notes when optional components are absent. The provider reference adds a further warning that several provider paths may be technically viable at once, so the harness in use should not be mistaken for the provider the user wants to bill or trust. The lifecycle reference adds one more warning: if registry state says a document is already known while its generated pages have been lost, future ingest may quietly preserve the gap rather than fixing it, so quality work includes coherence checks after merges and recoveries. It also warns that example and fixture files can compile into misleading project concepts unless they are clearly marked in the source, making staged input quality part of output quality. The workflow reference adds that deterministic staging only works when Git history, normalization policy, graph exclusion, vendored-skill readiness, and source-pack ordering are respected together; skipping one of those controls weakens the whole gate system. The validator summary adds that link scanning, reserved-file handling, and operational-area exclusions are also policy choices that must stay coherent with repository structure, or the quality gate can become noisy or misleading. The source-pack builder makes the same point operationally: if source paths are mis-selected, stale, or grouped incorrectly, the KB will ingest the wrong evidence even if the syntax is valid.

A practical implication is that quality work in this repo includes both enforcing formal rules and improving how isolated material is connected back to core workflows and standards. It also includes deciding when not to proceed automatically: stopping for consent, checking current tool readiness before ingesting, verifying package identity before install, validating after merges or reverts, using dry-runs before cleanup, disclosing provider routing before model-backed commands, refreshing Graphify before recompilation, keeping `okf/` out of the graph, reviewing generated wiki changes against their sources, repairing registry drift through supported commands, and choosing deterministic CI gates over non-blocking health reports are all part of maintaining trustworthy outputs. The prereq checker adds a further implication: early machine-readable diagnostics are not just convenience tooling but part of the repository's quality posture, because they make missing requirements visible before those gaps can distort later build or ingest steps. The validator script adds a parallel implication at the artifact layer: early structural diagnostics, even when only warnings, help catch truncation, malformed frontmatter, broken navigation, and naming collisions before they harden into persistent wiki damage. The source-pack builder adds that the same is true for staging: early normalization, deterministic bundling, and split-not-crop handling prevent lossy inputs from entering the pipeline. The editorial pass script adds the same implication for manual curation: a guarded edit is only trustworthy if the diff preserves scope, source provenance, and link integrity, and if the installed toolchain can reproduce the vendor's own wiki-target constraints.
