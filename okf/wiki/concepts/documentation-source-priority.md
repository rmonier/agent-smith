# Documentation Source Priority

Documentation source priority is the practice of consulting sources in a deliberate order so repository decisions rely on the most authoritative, current, and context-appropriate evidence first. It helps agents and maintainers avoid guesswork, preserve alignment with real tool behavior, and make clear when weaker or derivative sources are being used.

## Core idea

Documentation sources are not interchangeable. When setup rules, workflow expectations, or tool semantics may vary by environment or version, the safest approach is to rank sources by authority and immediacy, then consult them in that order. The goal is to prefer the source closest to the active repository and runtime before falling back to broader references.

In the harness documentation workflow described by `summaries/agents__skills__subagent-profile-adapter__references__harness-docs-md`, the prescribed order is:

1. Official local documentation shipped with the harness in the current environment.
2. Official web documentation.
3. User-provided documentation URL or snippet.
4. Community examples only as secondary evidence.

The same pattern appears in agent-ready repository guidance and in the OpenKB lifecycle for OKF maintenance. The managed `AGENTS.md` section generated by `summaries/agents__skills__agent-ready-context__scripts__merge_agents_md_okf_section-py` tells agents to consult repository context in a fixed sequence: `AGENTS.md` first for repository rules and navigation, then `okf/wiki/index.md` for compiled durable context, then `graphify-out/` for structural orientation, and only after that `.agents/skills/` for reusable executable procedures. The `summaries/agents__skills__agent-ready-context__assets__agents-md-okf-ready-template-md` template adds a related rule set for KB operations: read `AGENTS.md` for operational basics, then `okf/wiki/index.md` as the first routed knowledge source, then `graphify-out/GRAPH_REPORT.md` and `graphify-out/graph.json` for structure, and then `.agents/skills/` for reusable actions. This extends documentation source priority from documentation lookup into repository operating order, reinforcing [[concepts/agent-context-layering]] and [[concepts/context-action-separation]].

## Why this matters

This priority order helps preserve [[concepts/spec-authority]] by giving precedence to sources that define or directly describe repository truth over interpretation, generated views, or examples. It also reflects [[concepts/offline-first-workflows]] and [[concepts/external-documentation]] concerns: local and repository-resident materials are often both more available and better matched to the checked-out state, while web documentation may be newer but not necessarily version-aligned.

The approach also strengthens [[concepts/provenance-tracking]]. If a workflow, adapter, or wiki update is derived from a known, ranked source, later reviewers can understand why a choice was made and whether a refresh is needed. In the OpenKB lifecycle, this matters because the compiled wiki is explicitly treated as data rather than instructions, while executable guidance belongs in skills and repository instructions. That separation reduces the risk of treating secondary or generated material as primary authority.

## Practical application

In the harness-adapter workflow described by `summaries/agents__skills__subagent-profile-adapter__references__harness-docs-md`, source priority is not only about reading the right material. It also drives what gets recorded in the tooling context page:

- the official source URL or local reference;
- the retrieval timestamp;
- the supported profile or subagent paths;
- required frontmatter fields;
- permissions or tool model, if documented;
- instruction-file behavior, if documented;
- the generation policy chosen by the user.

In the repository knowledge workflow described by `summaries/agents__skills__agent-ready-context__references__openkb-lifecycle-md`, source priority also determines operational behavior:

- repository rules are read from `AGENTS.md` before any compiled or generated artifact;
- compiled wiki pages in `okf/wiki/` are consulted for durable context, not treated as command sources;
- graph outputs are used to choose files to inspect, not as final authority;
- reusable skills are consulted for repeatable actions after context has been established;
- external URLs are materialized as evidence with provenance before ingestion;
- source staging, hash registry coherence, and recompile steps preserve the lineage from repository file to generated page.

The `summaries/agents__skills__agent-ready-context__assets__agents-md-okf-ready-template-md` template also reinforces operational basics that should stay in `AGENTS.md`: primary language and toolchain versions, setup/build/launch commands, and the test invocation. More durable conventions and rationale belong in the OKF wiki, with a pointer to `okf/wiki/index.md` rather than deep links into compiled pages. That keeps operational orientation separate from durable knowledge and turns source selection into an auditable documentation step rather than an informal research habit. This behavior aligns with [[concepts/tooling-context-pages]], [[concepts/generated-content-governance]], [[concepts/okf-validation]], and [[concepts/data-flow-disclosure]].

## Interpretation guidelines

A source-priority rule does not mean lower-priority sources are useless. It means they should be used in ways appropriate to their trust level and role:

- Official local docs are strongest when environment-specific behavior matters.
- Official web docs are the next fallback when local docs are absent or incomplete.
- User-provided materials can clarify intent, but they should not automatically outrank official references.
- Community examples may help with patterns or edge cases, but they should support, not define, expected behavior.
- Repository navigation artifacts such as graph reports can help locate relevant files, but they should not replace direct inspection of source files or repository instructions.
- Compiled knowledge artifacts can summarize durable context, but they should not be mistaken for executable policy when a repository instruction or source document is the stronger authority.

This staged approach is closely related to [[concepts/source-trust-levels]], [[concepts/evidence-staging]], and [[concepts/index-based-discovery]].

## Risks it prevents

Following documentation source priority reduces several common failures:

- building adapters or workflows from outdated assumptions;
- overfitting to unofficial examples or generated summaries;
- missing version-specific behavior present only in shipped docs or repository-local instructions;
- using graph or wiki outputs as if they were authoritative command sources;
- producing context pages without clear evidence lineage;
- creating generated artifacts that cannot be justified during review;
- skipping KB reconciliation steps and letting registry drift hide stale or missing pages.

These protections reinforce [[concepts/quality-gates]], [[concepts/deterministic-validation]], [[concepts/wikilink-integrity]], and [[concepts/human-in-the-loop-review]] when documentation outputs are later incorporated into a structured knowledge system.

## Relationship to adjacent concepts

Documentation source priority overlaps with but is distinct from related ideas:

- [[concepts/spec-authority]] focuses on which source defines truth.
- [[concepts/provenance-tracking]] focuses on recording where decisions came from.
- [[concepts/tooling-context-pages]] focuses on where adapter-relevant findings are stored.
- [[concepts/external-documentation]] focuses on how outside references are incorporated.
- [[concepts/agent-context-layering]] focuses on how repository instructions, compiled context, structural maps, and skills are separated by role.
- [[concepts/context-action-separation]] focuses on keeping durable knowledge distinct from executable procedure.
- [[concepts/registry-drift]] captures the operational risk of stale KB registry state when generated pages go missing or stop matching their source set.

Documentation source priority connects these ideas into a decision rule: choose the strongest source first, use derivative artifacts according to their intended role, and record the basis for downstream work.
