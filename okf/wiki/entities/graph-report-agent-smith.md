# Graph Report - agent-smith

## What it is
Graph Report - agent-smith is a structural analysis artifact generated by [[entities/graphify]] for the [[entities/agent-smith]] repository. It maps repository files, headings, functions, and documentation sections as a graph, then highlights hubs, communities, and weakly connected areas. This makes it a repository exploration and diagnostics work focused on [[concepts/knowledge-graph-analysis]] and [[concepts/repository-overview-generation]].

## Source and context
This entity is documented directly in [[summaries/graphify-report]] and is used by the repository staging and overview-generation workflow, including [[summaries/agents__skills__agent-ready-context__scripts__build_okf_source_pack-py]] and [[summaries/agents__skills__agent-ready-context__scripts__build_okf_skeleton-py]]. In that workflow, the report is treated as a staged input artifact: it can be copied into OpenKB-compatible input as `graphify-report.md`, then reused as evidence for conservative repository overview generation. The staging script treats it as useful structural evidence, but only after normalizing run-dependent timestamps and checking that it does not accidentally describe generated KB output. This places the report alongside repository guidance and validation material connected to [[entities/agents-md]], [[entities/openkb]], and [[entities/agent-ready-context]], while also linking it to [[concepts/evidence-staging]], [[concepts/self-reference-control]], and [[concepts/repository-ingestion]].

## Key facts
- It analyzes a corpus of 53 files and about 41,382 words.
- It reports 369 nodes, 378 edges, and 49 communities, with 41 communities shown and 8 thin communities omitted.
- Its extraction is fully structural: 100% extracted, with no inferred or ambiguous edges.
- It was built from commit `1639ea0c`, with a recommendation to compare against current HEAD and refresh using `graphify update .` after code changes.
- It detects no import cycles and no surprising cross-file connections.
- In the OKF staging workflow, it can be read from `graphify-out/GRAPH_REPORT.md`, normalized, and staged as `okf/.okf-build/input/graphify-report.md`.
- That staged copy removes timestamp lines and date suffixes in headings so unchanged reports keep stable hashes, supporting [[concepts/deterministic-builds]] and [[concepts/line-ending-normalization]].
- The staging script records per-file provenance for the staged report and includes it in a source-pack manifest when accepted, linking the artifact to [[concepts/staging-manifests]] and [[concepts/provenance-tracking]].
- The same workflow explicitly refuses to stage the report if it appears to reference generated KB paths under `okf/` repeatedly, to avoid a self-referential ingestion loop.
- In the skeleton workflow, the report is also excerpted into a generated repository overview page, and that downstream use remains explicitly conservative and subject to later review.

## Main findings
The report identifies a small set of strong repository hubs and many weakly connected nodes. This suggests a codebase with clear major guidance centers but uneven cohesion across documentation and implementation surfaces.

Key high-connectivity nodes include:
- `main()` entrypoints
- OKF quality and offline conformance baseline
- What You Must Do When Invoked
- `/graphify`
- OpenKB Wiki Schema
- `AGENTS.md`

These hubs indicate the repository is organized around validation workflows, agent guidance, repository instructions, and knowledge-base conventions. That pattern relates closely to [[concepts/documentation-architecture]], [[concepts/agent-context-layering]], [[concepts/okf-validation]], and [[concepts/repo-navigation]]. The fact that later scripts reuse the report as staged evidence and as an overview excerpt also shows that this work functions as practical source material for [[concepts/llm-free-knowledge-bootstrap]], not just as an inspection artifact.

## Community structure
The report groups the repository into communities centered on several major areas:
- `README.md` as a broad onboarding and policy surface
- build and validation scripts such as source-pack and bundle validation tools
- OpenKB and OKF governance documents
- skill and profile guidance for agent workflows
- Graphify operational reference material

This organization reflects a repository where procedural knowledge, validation logic, and agent-facing instructions are first-class components. It connects to [[concepts/action-oriented-documentation]], [[concepts/executable-validation]], [[concepts/generated-content-governance]], and [[concepts/skill-based-automation]]. Its reuse by the source-pack builder and skeleton builder also links it to staged evidence handling, repository ingestion, and overview generation practices that support [[concepts/evidence-staging]], [[concepts/index-based-discovery]], and [[concepts/repository-ingestion]].

## Quality signals and limitations
Positive signals in the report include clean structural extraction and the absence of import cycles. However, it also flags notable fragmentation:
- 208 isolated nodes have one or fewer connections
- 8 thin communities are omitted from the main report
- the `README.md` cluster has very low cohesion
- the `What You Must Do When Invoked` cluster also has low cohesion

These findings suggest opportunities to improve modularity, cross-linking, and content structure, especially around [[concepts/documentation-cohesion]], [[concepts/index-based-discovery]], and [[concepts/wikilink-integrity]]. The staging workflow introduces an additional operational limitation: the report is accepted only if it does not appear to map generated KB output under `okf/`, because such self-reference would feed compiled wiki descriptions back into later ingestion. That makes the report valuable but conditionally trusted evidence, shaped by [[concepts/self-reference-control]], [[concepts/knowledge-boundaries]], and [[concepts/safe-automation]]. A further limitation remains in downstream overview generation: only the first portion of the report may be copied into a generated overview, so later wiki output can preserve the report as evidence while still requiring [[concepts/human-in-the-loop-review]] for fuller interpretation.

## Why it matters
Graph Report - agent-smith provides a compact structural picture of how the repository is actually organized. Rather than describing intended architecture, it reveals where attention, coupling, and fragmentation appear in practice. That makes it useful for navigation, refactoring decisions, and documentation maintenance, especially in a repository shaped by [[entities/openkb]], [[entities/graphify]], and agent-ready workflow conventions. It also matters operationally because the OKF source-pack builder treats it as normalized, provenance-bearing staged evidence, while also defending against self-referential ingestion loops. This ties the work to [[concepts/llm-free-knowledge-bootstrap]], [[concepts/provenance-tracking]], [[concepts/graceful-degradation]], [[concepts/deterministic-builds]], and [[concepts/self-reference-control]].
