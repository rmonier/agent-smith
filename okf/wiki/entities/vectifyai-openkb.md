# VectifyAI/OpenKB

VectifyAI/OpenKB is the upstream work behind [[entities/openkb]] and the semantic knowledge compiler referenced throughout this wiki for repository-scoped knowledge-base maintenance. Across the current sources, it is treated as the authoritative external work for how `okf/` and `okf/wiki/` are initialized, staged, ingested, linted, reviewed, validated, repaired, and kept structurally grounded over time under a consent-first workflow. It is directly connected to [[entities/openkb]], [[entities/agent-smith]], [[entities/agent-ready-context]], [[entities/graphify]], [[entities/litellm]], and [[entities/pageindex]].

## Role in skill management

The document [[summaries/agents__skills__skill-creator__references__vendor-skill-management-md]] uses [[entities/vectifyai-openkb]] as the source of the `openkb` vendor skill and optional deck helper skills such as `openkb-deck-editorial`, `openkb-deck-neon`, and `openkb-html-critic`. These are presented as typical vendor skills: they should be vendored into the target repository at project scope, pinned to a known version, and kept immutable after import.

The dependency reference in [[summaries/agents__skills__agent-ready-context__references__dependencies-md]] makes that workflow more explicit. It treats VectifyAI/OpenKB as the authoritative upstream repository to consult when confirming package identity, reviewing release notes, and manually vendoring `skills/openkb/` from the pinned version tag because the main OpenKB CLI skill does not ship with a project-scoped installer. In this model, the vendored `openkb` skill must exist at `.agents/skills/openkb/` before the pipeline invokes the CLI, and optional deck or critic skills remain separate top-level vendor directories rather than nested assets. This strengthens the repository's role in [[concepts/skill-vendoring]], [[concepts/skill-structure-conventions]], and [[concepts/documentation-source-priority]].

The summary of [[summaries/agents__skills__agent-ready-context__scripts__check_prereqs-py]] adds a more explicit enforcement layer around that same relationship. The preflight script treats the OpenKB CLI as optional, but if the CLI is installed it expects the vendored skill at `.agents/skills/openkb/SKILL.md` to be present before first use. Missing vendoring in that state is surfaced as a diagnostic note rather than a hard failure, which makes VectifyAI/OpenKB part of the repository's practical model for staged adoption, explicit dependency readiness, and [[concepts/graceful-degradation]] under [[concepts/preflight-checks]].

The summary [[summaries/agents__skills__agent-ready-context__SKILL-md]] adds that vendoring is not a convenience but part of tool adoption itself. Before the first `openkb` or `graphify` CLI invocation, the corresponding read-only vendor skill must be copied into `.agents/skills/` under the same user consent that approved installing the tool. The same source frames this as part of the repository's policy split between reusable actions and durable context, reinforcing VectifyAI/OpenKB's role in [[concepts/skill-governance]], [[concepts/context-action-separation]], and [[concepts/tooling-consent-and-pin-management]].

The README for [[entities/agent-smith]] adds a second role: VectifyAI/OpenKB is also the upstream project for the OpenKB compiler itself, which agent-smith uses to initialize, ingest, lint, and recompile `okf/wiki/` bundles as part of [[concepts/repository-ingestion]], [[concepts/incremental-compilation]], and [[concepts/okf-validation]]. It is also named as the source of an optional Skill Factory packaging path, where generated skills under `okf/output/skills/` may be adopted only after validation.

The lifecycle reference [[summaries/agents__skills__agent-ready-context__references__openkb-lifecycle-md]] adds the most detailed operational role for this upstream work. It defines the command-level maintenance policy around OpenKB: read-first inspection with `status` and `list`, deterministic staged ingestion, dry-run-first removal and recompilation, cautious use of LLM-backed commands, and explicit separation between generated output and hand-authored wiki context. It also frames OpenKB as the semantic engine for OKF maintenance, identifies `okf/` as the KB root and `okf/wiki/` as the compiled wiki, and treats `openkb lint` as a health report rather than a gate. In effect, the upstream repository anchors not just distribution of skills and binaries but the repository's whole model of [[concepts/generated-content-governance]], [[concepts/source-driven-regeneration]], [[concepts/quality-gates]], and [[concepts/validation-vs-health-reporting]].

The same lifecycle reference also adds a detailed findings and recovery model. It distinguishes captured findings in `okf/wiki/explorations/findings/` from compiled wiki content, requires promotion through staged `finding-*` docs, and makes clear that registry drift can leave wiki holes when `hashes.json` and generated pages get out of sync. That makes VectifyAI/OpenKB central to [[concepts/findings]], [[concepts/findings-promotion]], [[concepts/registry-drift]], and [[concepts/hash-registry-coherence]].

The provider reference [[summaries/agents__skills__agent-ready-context__references__openkb-providers-md]] expands that role into runtime configuration. It treats VectifyAI/OpenKB as the upstream source for choosing how OpenKB talks to external model providers through litellm, including explicit model naming in `okf/.openkb/config.yaml`, credential resolution order, provider-specific routing choices, and mandatory disclosure before staged content is sent to an LLM-backed command. This connects the repository directly to [[concepts/provider-integration]], [[concepts/configuration-precedence]], [[concepts/data-flow-disclosure]], and [[concepts/local-vs-shared-configuration]].

The privacy and data-flow reference [[summaries/agents__skills__agent-ready-context__references__privacy-and-data-flows-md]] sharpens that operational role further by treating VectifyAI/OpenKB as the upstream source for explicit egress control and offline-preserving workflow design. It requires disclosure before any step that sends repository content off-machine, including the tool, provider or endpoint, model, credential source, and the content being sent. It also requires explicit routing rather than silent provider selection, preserving a fully local air-gapped path and a zero-LLM path, and re-verifying no-telemetry claims whenever a pin changes. In that framing, the upstream repository shapes not just how providers are configured, but how consent, routing, staging, and local fallback are enforced across the knowledge pipeline. This adds direct links to [[concepts/privacy-preserving-tooling]], [[concepts/explicit-provider-routing]], [[concepts/offline-first-workflows]], and [[concepts/llm-free-knowledge-bootstrap]].

The same privacy reference also records the stage-by-stage data flows for the pipeline. Local prerequisite checks, source packing, skeleton generation, and validators keep data on-machine; code-only graphify runs stay local; non-code graphify runs may send document content to the selected backend; OpenKB commands can send staged sources, wiki pages, and prompts to the configured provider; PageIndex remains local unless `PAGEINDEX_API_KEY` is set; and URL ingestion or web evidence gathering can introduce network fetches. It also says cost and cache artifacts are local generated files that should stay gitignored. These constraints deepen VectifyAI/OpenKB's connection to [[concepts/tool-boundaries]], [[concepts/offline-first-workflows]], [[concepts/privacy-preserving-tooling]], and [[concepts/generated-content-governance]].

The same document adds a specific path-safety rule: staging must live inside the KB root at `okf/.okf-build/input/`, never outside it. The reason is that `okf/.openkb/hashes.json` stores KB-relative paths only for files staged inside the root, while outside-root ingestion can record absolute machine paths and leak usernames and directory structure into committed registry state. That makes VectifyAI/OpenKB a direct source for [[concepts/kb-root-staging]], [[concepts/hash-registry-coherence]], [[concepts/path-safety]], and [[concepts/provenance-tracking]].

The README for [[entities/agent-smith]] adds a second operational constraint: OpenKB is configured explicitly, participates in [[concepts/data-flow-disclosure]], and is used inside deterministic staging and validation flows tied to [[concepts/deterministic-builds]], [[concepts/evidence-staging]], and [[concepts/provenance-tracking]].

The workflow reference [[summaries/agents__skills__agent-ready-context__references__workflow-md]] extends this further into the repository build process itself. It presents VectifyAI/OpenKB as the upstream work defining the full repo-to-wiki pipeline: prerequisite gating, consent-first optional tool bootstrap, vendoring of the OpenKB skill before CLI use, initialization of `okf/`, staged ingestion from `okf/.okf-build/input/`, post-generation review, and validator-backed acceptance of compiled output. It also ties OpenKB directly to requirements for deterministic source-pack construction, correction-loop regeneration instead of hand-editing generated pages, and keeping the compiled wiki out of the Graphify graph. That makes this upstream repository a direct source for [[concepts/deterministic-builds]], [[concepts/evidence-staging]], [[concepts/human-in-the-loop-review]], and [[concepts/self-reference-control]].

The summary [[summaries/agents__skills__agent-ready-context__SKILL-md]] reinforces the same point at the policy level. It defines the durable context source of truth as `okf/wiki/`, keeps `AGENTS.md` limited to orientation, and rejects parallel wikis or long-form repository knowledge in agent instructions. It also states that generated pages should not be hand-corrected when source improvements and re-ingestion are possible, which further ties this upstream work to [[concepts/durable-context]], [[concepts/single-source-of-truth]], and [[concepts/source-driven-regeneration]].

The Graphify report adds structural evidence that these responsibilities are not peripheral. In [[summaries/graphify-report]], OpenKB appears as one of the named entities surfaced by repository-wide graph extraction, and OpenKB-related workflow communities are among the strongest visible clusters. The report highlights communities around OpenKB lifecycle maintenance, repository build workflow, provider configuration, validation, and tooling policy, showing that upstream OpenKB conventions shape major parts of the repository's documentation and operational graph.

This makes the repository relevant to [[concepts/skill-governance]], [[concepts/dependency-management]], [[concepts/version-pinning]], [[concepts/supply-chain-security]], and [[concepts/generated-artifact-adoption]]. The guidance consistently treats artifacts from this source as external dependencies rather than project-owned instructions.

## Handling guidance

When content from VectifyAI/OpenKB is adopted as a vendor skill, the source documents say it should be:

- reviewed before installation, including publisher, repository, license, and skill contents
- pinned through the manager and lock file when available
- recorded with source and version metadata
- left unedited after vendoring
- updated only by re-vendoring or manager-based upgrade

The dependency guidance in [[summaries/agents__skills__agent-ready-context__references__dependencies-md]] adds stricter supply-chain handling around the same source. It says the exact package name and upstream repository must be verified before install, the configured Python index must be respected rather than bypassed, exact versions must be pinned in commands left behind, and integrity hashes from the configured index must be recorded and compared on later installs. A same-version hash mismatch is treated as a stop-and-report event rather than something to silently repair. These rules tie the repository directly to [[concepts/trust-on-first-use]], [[concepts/integrity-pinning]], [[concepts/hash-registry-coherence]], and [[concepts/tooling-consent-and-pin-management]].

The summary of [[summaries/agents__skills__agent-ready-context__scripts__check_prereqs-py]] adds repository-readiness handling around the same toolchain. Its preflight behavior says OpenKB itself is optional, but when present it should be accompanied by the vendored `.agents/skills/openkb/` copy before the CLI is invoked. The same script also presents OpenKB installation as a consent-gated action via a pinned `uv tool install` path, while preserving a conservative skeleton-only fallback when the tool is unavailable. That makes VectifyAI/OpenKB part of the repository's handling rules for [[concepts/tooling-consent-and-pin-management]], [[concepts/graceful-degradation]], and [[concepts/executable-validation]].

The README for [[entities/agent-smith]] reinforces the same operating stance for the OpenKB toolchain itself: installations are consent-first, version-pinned, integrity-recorded, and validated as part of a broader [[concepts/tooling-consent-and-pin-management]] workflow. OpenKB is configured explicitly, participates in [[concepts/data-flow-disclosure]], and is used inside deterministic staging and validation flows tied to [[concepts/deterministic-builds]], [[concepts/evidence-staging]], and [[concepts/provenance-tracking]].

The lifecycle guidance in [[summaries/agents__skills__agent-ready-context__references__openkb-lifecycle-md]] makes the handling rules more concrete for live KB maintenance. It says operators should inspect the KB before acting, use dry runs before destructive changes, disclose when commands trigger URL fetches or LLM-backed lint/query behavior, and keep staging inside `okf/` when possible to avoid privacy leaks from absolute paths in the hash registry. It also sets a strict no-hand-edit rule for `okf/raw/` and generated wiki pages, reserving manual authorship for approved convention pages such as `okf/wiki/AGENTS.md` and hand-authored tooling context. These policies reinforce [[concepts/privacy-preserving-tooling]], [[concepts/data-flow-disclosure]], [[concepts/safe-automation]], and [[concepts/tooling-context-pages]].

The provider guidance in [[summaries/agents__skills__agent-ready-context__references__openkb-providers-md]] adds specific operational constraints for LLM-backed use. It says provider and model selection must be explicit, committed only in `okf/.openkb/config.yaml`, and not duplicated into `AGENTS.md` or other orientation files. It also defines a precedence order for credentials, a harness-aware provider selection flow, and a default expectation that operators disclose tool, provider, model, endpoint, credential source, and what staged content will be sent before the first LLM-backed add, recompile, lint, query, chat, skill, or deck command. That makes this upstream work a direct source for the repository's rules around [[concepts/single-source-of-truth]], [[concepts/harness-vs-local-tools]], [[concepts/runtime-ambiguity-resolution]], and [[concepts/privacy-preserving-tooling]].

The same privacy document also clarifies that OpenKB has no telemetry, analytics, or update checks in the verified version, and that the privacy-relevant egress points are the configured model provider, optional PageIndex cloud use, approved URL fetches, and browser-based feedback. That extends this upstream repository's importance for [[concepts/telemetry-auditing]], [[concepts/privacy-preserving-tooling]], and [[concepts/tooling-consent-and-pin-management]].

The privacy reference also clarifies that PageIndex processing is local by default and only becomes cloud upload behavior when `PAGEINDEX_API_KEY` is set, while local runtimes such as [[entities/ollama]] and [[entities/lm-studio]] may need long timeouts and dropped unsupported parameters. That strengthens the repository's connection to [[concepts/offline-first-workflows]], [[concepts/graceful-degradation]], and [[concepts/tool-boundaries]] by showing how upstream OpenKB distinguishes between local processing, cloud services, and zero-LLM fallback paths.

The same lifecycle document also warns that `okf/.openkb/hashes.json` and `okf/wiki/` must be treated as a coupled unit. If registry entries survive while generated pages are lost, future ingests can silently skip damaged documents, producing durable holes until explicit repair through recompilation or registry cleanup. That makes this upstream repository a direct source for the repository's rules around [[concepts/registry-drift]], [[concepts/hash-registry-coherence]], and [[concepts/source-driven-regeneration]].

The workflow reference [[summaries/agents__skills__agent-ready-context__references__workflow-md]] adds additional operating rules around the same source. It requires prerequisite checks before build steps, explicit user consent before bootstrapping optional tooling, vendoring of `.agents/skills/openkb/` before first CLI use, and merge-not-replace handling for `.gitattributes` and `.graphifyignore`. It also frames post-generation inspection as mandatory review work: changed wiki pages must be read for missing concepts, near-duplicates, classification mistakes, lost caveats, truncation, stale early pages, and grounding gaps, with every issue routed through committed-source fixes and regeneration instead of hand-editing outputs. These rules further connect the repository to [[concepts/git-attributes]], [[concepts/caveat-preservation]], [[concepts/source-driven-regeneration]], and [[concepts/human-in-the-loop-review]].

The same workflow source also makes the self-reference policy explicit: the KB root must stay out of Graphify, and graph reports that reference `okf/` are rejected because they break incremental convergence, create circular grounding, and pollute discovery with generated summaries of generated summaries. This tightens the handling stance around [[concepts/self-reference-control]], [[concepts/knowledge-boundaries]], [[concepts/index-based-discovery]], and [[concepts/deterministic-builds]].

The summary [[summaries/agents__skills__agent-ready-context__SKILL-md]] adds several handling requirements at the top level of the workflow. It requires `uv run` for bundled scripts, treats `uv` as the mandatory Python toolchain, forbids broad OpenKB operations such as `lint --fix`, `remove`, `recompile --all`, `query`, `watch`, `chat`, or Skill Factory commands without consent, and frames `openkb lint` as a health check rather than a reason to auto-rewrite outputs. It also defines build artifact hygiene for `okf/.okf-build/`, `okf/output/`, `okf/wiki/reports/`, and most of `okf/.openkb/`, which deepens the repository's ties to [[concepts/cross-platform-tooling]], [[concepts/validation-vs-health-reporting]], [[concepts/generated-content-governance]], and [[concepts/deterministic-validation]].

The Graphify report reinforces this handling guidance indirectly by showing that provenance, dependency management, tooling consent and pin management, provider integration, and OpenKB lifecycle maintenance are all high-connectivity parts of the repository graph in [[summaries/graphify-report]]. That structural prominence suggests these rules are not just local recommendations; they are central organizing constraints in how the repository uses upstream OpenKB assets.

If project-specific behavior is needed, the recommended approach remains to create a separate companion skill instead of modifying the vendored copy. This preserves [[concepts/single-source-of-truth]] for upstream assets while keeping local procedures under project control.

## Relationship to OpenKB

This repository is the upstream home of [[entities/openkb]], the tool that agent-smith uses as its semantic knowledge compiler for building and maintaining `okf/wiki/` bundles in the style of [[concepts/llm-wiki]] and [[concepts/durable-context]]. In the README, OpenKB is not just cited as background technology; it is part of the core architecture for converting repositories into [[concepts/agent-ready-repositories]] through compiled knowledge, incremental updates, and validated outputs.

The dependency reference in [[summaries/agents__skills__agent-ready-context__references__dependencies-md]] adds an important operational nuance: the repository is not only the conceptual upstream home of OpenKB but also the practical source of truth for release review and vendored skill acquisition. Because the wheel does not include the main CLI skill and the documented harness integrations are user- or harness-scoped, the repo tag itself becomes the project-scoped source for copying `skills/openkb/` into the target repository. That makes VectifyAI/OpenKB central to both tool installation governance and repository-local knowledge durability, linking it to [[concepts/spec-authority]], [[concepts/provenance-tracking]], and [[concepts/agent-context-layering]].

The lifecycle reference [[summaries/agents__skills__agent-ready-context__references__openkb-lifecycle-md]] sharpens that picture substantially. It presents OpenKB as the semantic engine for the OKF lifecycle and defines the repository's expectations for how a converted repo should use it: `okf/` as KB root, `okf/wiki/` as compiled wiki, `status` and `list` as read-first commands, deterministic staged input as the authoritative update path, and `recompile` as the repair mechanism for stale or damaged generated pages. It also distinguishes between a strict validator and non-gating health reporting, making this upstream work central to [[concepts/quality-gates]], [[concepts/executable-validation]], [[concepts/generated-content-governance]], and [[concepts/validation-vs-health-reporting]].

That same source also clarifies the provenance chain managed by OpenKB: generated concept and entity pages point back through summaries to staged source copies with source path, source hash, and source commit metadata. This makes VectifyAI/OpenKB important not only as a compiler project but also as the upstream work defining the repository's model for [[concepts/knowledge-linking-and-citations]], [[concepts/frontmatter-metadata]], and [[concepts/provenance-tracking]].

The provider reference [[summaries/agents__skills__agent-ready-context__references__openkb-providers-md]] adds another important nuance to that relationship. It shows that upstream OpenKB defines not just compilation behavior but also the boundary between repository-local configuration and external provider access: litellm model names, credential lookup order, optional OAuth-style subscription paths, local-runtime options, and zero-LLM fallback are all routed through OpenKB's configuration model rather than scattered across general agent instructions. In practice, that makes VectifyAI/OpenKB central to [[concepts/provider-integration]], [[concepts/configuration-precedence]], [[concepts/harness-native-profiles]], and [[concepts/llm-free-knowledge-bootstrap]].

The same provider guidance also makes clear that OpenKB's repository model includes explicit disclosure obligations whenever staged content is sent to a remote provider, while preserving the possibility of local-only operation through local runtimes and local PageIndex defaults. This positions VectifyAI/OpenKB as an upstream work that materially shapes both the privacy posture and the runtime flexibility of repository knowledge compilation, aligning it with [[concepts/privacy-preserving-tooling]], [[concepts/offline-first-workflows]], and [[concepts/tool-boundaries]].

The privacy and data-flow reference deepens that relationship by framing OpenKB as an upstream source of mandatory privacy commitments rather than optional best practices. It defines transparency before remote processing, explicit routing through configured providers, preservation of air-gapped and zero-LLM workflows, and re-verification of no-telemetry claims whenever pins change. It also makes the OpenKB repository model responsible for preventing path leakage through outside-root staging and for preserving consent-based operation when URL ingestion, document processing, or remote compilation paths are used. This further ties VectifyAI/OpenKB to [[concepts/data-flow-disclosure]], [[concepts/explicit-provider-routing]], [[concepts/kb-root-staging]], and [[concepts/telemetry-auditing]].

The workflow reference [[summaries/agents__skills__agent-ready-context__references__workflow-md]] sharpens the broader architectural view by making the full repository build workflow part of OpenKB's upstream role. It defines the order of Graphify refresh, source-pack creation, OpenKB initialization, staged ingestion, linting, validation, AGENTS merge, and post-generation review; treats deterministic staging as a precondition for hash-based deduplication; and requires correction-loop regeneration for problems found in generated pages. It also explicitly reserves skeleton-only output for no-provider cases rather than overstating completeness. This positions VectifyAI/OpenKB as an upstream work that shapes [[concepts/repository-ingestion]], [[concepts/deterministic-validation]], [[concepts/graceful-degradation]], and [[concepts/generated-content-governance]].

The summary [[summaries/agents__skills__agent-ready-context__SKILL-md]] strengthens that architectural relationship by naming `okf/wiki/` as the durable context source of truth, `AGENTS.md` as an orientation layer, and skills as the action layer. It forbids parallel repository wikis, requires deterministic staged input under `okf/.okf-build/input/`, and treats the OpenKB-owned KB directories as a managed surface rather than a manually maintained notes area. This positions VectifyAI/OpenKB as one of the core upstream works behind [[concepts/agent-context-layering]], [[concepts/documentation-architecture]], [[concepts/durable-context]], and [[concepts/kb-root-staging]].

The same source also defines the official operating boundary around generated output: weak wiki pages should be repaired through better source documents and re-ingestion, not direct edits; `okf/.openkb/hashes.json` is a critical deduplication registry; and `okf/wiki/tooling/` plus approved convention pages are rare exceptions to the no-direct-write rule. Those constraints further connect VectifyAI/OpenKB to [[concepts/incremental-compilation]], [[concepts/hash-registry-coherence]], [[concepts/registry-drift]], and [[concepts/source-driven-regeneration]].

The summary of [[summaries/agents__skills__agent-ready-context__scripts__check_prereqs-py]] adds a final practical connection: before OpenKB is even used, the repository's own preflight logic checks whether `uv` is available, whether the repository is writable in expected KB and skill locations, whether the OpenKB CLI is installed, and whether the corresponding vendored skill is present when needed. That makes VectifyAI/OpenKB part of the operational boundary between repository preparation and compilation, connecting it directly to [[concepts/preflight-checks]], [[concepts/filesystem-validation]], [[concepts/cross-platform-tooling]], and [[concepts/validation-vs-health-reporting]].

The same workflow source also codifies the policy that the wiki must stay out of the repository graph, because self-mapping breaks fixed-point behavior, provenance grounding, and discovery quality. That makes VectifyAI/OpenKB part of the repository's architectural stance on [[concepts/self-reference-control]], [[concepts/knowledge-graph-analysis]], and [[concepts/documentation-architecture]].

The Graphify report sharpens the broader architectural view by showing OpenKB-centered material as part of the repository's main structural pattern. In [[summaries/graphify-report]], communities for OpenKB lifecycle maintenance, repository build workflow, provider integration, validation, and wiki schema all appear as strong thematic clusters, while OpenKB itself is listed as a named entity in the structural map. This positions VectifyAI/OpenKB not merely as an external reference but as one of the upstream works that anchor the repository's [[concepts/agent-context-layering]], [[concepts/main-structural-patterns]], and [[concepts/repository-overview-generation]].

The repository is also the source of official OpenKB read-only skills, which links its packaged outputs to [[concepts/skill-based-automation]] while keeping them separate from project-authored context and procedures. That positioning aligns with [[concepts/context-action-separation]] and [[concepts/knowledge-boundaries]]: OpenKB provides both a compiler and optional reusable assets, but those assets are still governed as imported upstream work.
