# Vendor and custom skill management

Use this reference when adding third-party skills or deciding whether to edit an existing skill.

## Vendor skills

Vendor skills are dependencies. They may be installed through a skill manager such as `skills.sh` or `npx skill` and should be pinned by the lock file generated by that manager, for example `skill-lock.json` when present.

Third-party skills are dependencies: vendor a pinned, reviewed copy only when the active repository workflow requires it, keep it immutable with its source version recorded, and create project-specific companion skills when behavior needs to change.

### Vendor skills vs adopted generated skills

Both end up under `.agents/skills/`, but they follow different rules:

- **Vendored vendor skills** are third-party content copied in read-only. Safety-review them before vendoring (rule 5 below), record source and version, and never edit them — not even to meet this repository's skill conventions. Update by re-vendoring a newer pinned version.
- **Adopted generated skills** (brought in from an explicitly selected source through `adopt_generated_skill.py`) become project-owned at adoption. They must pass `quick_validate.py` and skill-creator standards, and afterwards they are edited and maintained like any custom skill.

Adoption includes a caveat-preservation review: generation or distillation can flatten conditions into unconditional instructions. Before committing an adopted skill, compare it against the source material it came from. If that source is routed through the OKF wiki, begin at `okf/wiki/index.md` and follow its provenance to the underlying source documents. Confirm that constraints, boundaries, "only when", and "never do" statements survived, and restore any flattened caveat by editing the adopted copy — it is project-owned, so this is allowed and expected.

Rules:

1. Do not edit vendor skill files directly.
2. Update vendor skills only through the package/skill manager.
3. Commit the lock file when the manager creates one.
4. If project-specific behavior is needed, create a custom companion skill under `.agents/skills/`.
5. Before installing a vendor skill, verify its source (publisher, repository, license) and review its `SKILL.md` and scripts for surprising instructions; a skill is executable guidance and deserves the same scrutiny as a dependency.
6. Pin vendor skill versions through the manager/lockfile; do not track floating latest.

## Custom skills

Custom skills are project-owned action procedures. They live under `.agents/skills/<skill-name>/` and must follow Agent Skills directory and frontmatter rules.

Custom skills should be created when repeated actions are discovered in:

- OKF wiki pages
- AGENTS.md maintenance notes
- incident/runbook history
- repeated user prompts
- repeated agent command sequences

Keep the custom skill procedural and keep the context in `okf/wiki/`.
